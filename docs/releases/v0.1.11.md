### 为什么发这个版本

DSH `0.2.0-rc.1` 起在 profile 加载阶段强制执行 peer 范围门禁：bundle 声明的 `@deepseek-ai/dsh-*` peer 范围若不包含正在运行的 DSH 版本，会被直接跳过，不加载、不提示于页面。本插件此前声明的 `>=0.1.7-alpha.2 <0.2.0` 恰好能在 `0.2.0-rc.1` 上加载（预发布按 SemVer 排序小于 `0.2.0`，加载门禁将其纳入），但这是一颗**定时炸弹**：

- DSH `0.2.0` **正式版**发布当天，`<0.2.0` 将不再包含正在运行的版本，插件会被静默丢弃；
- 与 `0.1.6` 时期下界必须点名 `0.1.7-alpha.2` 是同一规则的镜像——上界同理不能裸写 `<0.2.0`。

因此本版把 `dsh.engines.dsh` 与 `peerDependencies['@deepseek-ai/dsh-settings']` 从 `>=0.1.7-alpha.2 <0.2.0` 放宽为 `>=0.1.7-alpha.2 <0.3.0`，与 `@idoall/dsh-notify` 0.4.1 的同类适配一致。

### 凭什么宣称为 `0.2.0-rc.1` 兼容

按仓库纪律「实测 → 记录 → 声明」，证据有三层：

- **活体证据**：本插件正以 `0.1.10` 的 manifest 加载并运行在当前 DSH `0.2.0-rc.1` profile 中（profile 启动无 skipping 警告，客户端芯片正常渲染）。
- **逐包核对**：`dsh.client.inject` 声明的 6 个宿主包（`dsh-api-remotes`、`dsh-client-connection`、`dsh-client-ui-layout`、`dsh-client-ui-sidebar`、`dsh-client-ui-settings(-general)`）与 peer `dsh-settings`，在 `dsh-v0.1.7-rc.2` → `dsh-v0.2.0-rc.1` 之间仅有版本号、README 双语化与 tsconfig 改动；仅有的两处源码变化是纯增量——`dsh-client-product-analytics` 的 remote 贡献挂载，以及 `selectPanel` 对两个面板点击的遥测埋点。本插件用到的接口面（`remote.settings`、`ctx.configForms`、sidebar 槽位、认证 Connection RPC）无一变化。
- **测试锁定**：`tests/shared/compatibility.spec.ts` 用仓库自带的含预发布排序的比较器断言两处范围接纳每一个已验证版本，`<0.3.0` 对四个版本全部通过。

### 改了什么

- **仅声明，零代码。** [`package.json`](../../package.json)：版本 `0.1.11`；`dsh.engines.dsh` 与 `peerDependencies['@deepseek-ai/dsh-settings']` 放宽为 `>=0.1.7-alpha.2 <0.3.0`；`dsh.compatibility.dshReleases` 新增 `"0.2.0-rc.1": "compatible"`。[`src/shared/types.ts`](../../src/shared/types.ts) 的 `VERIFIED_DSH_VERSIONS` 同步新增 `0.2.0-rc.1`（一致性测试保证两处清单逐字相同）。README（双语）与 CHANGELOG 同步。
- **不变**：宿主半、状态读取、RPC 路由、品牌行芯片、三种圆点状态、详情面板、局域网（非回环）回退、三个偏好字段——118 个测试全部通过。无需迁移。

### 谁受影响、需要做什么

- **正在 DSH `0.2.0-rc.1` 上运行 `0.1.10` 的人**：一切照旧。本版只是把既成事实写成声明；升级到 `0.1.11` 后，面板里的 `0.2.0-rc.1` 将从「尚未验证兼容」变为「已验证兼容」。
- **计划跟随 DSH `0.2.0` 正式版的人**：必须升级到 `0.1.11`（或更新）。留在 `0.1.10` 会在 DSH `0.2.0` 发布后被静默丢弃。
- **仍在 DSH `0.1.7` 线（含 `rc.2`/`rc.1`/`alpha.2`）的人**：`0.1.11` 与 `0.1.10` 声明等价（范围是超集），可直接升级；更早的 DSH（含 `0.1.6-alpha.2`）请继续用插件 `0.1.5`。

**Newest verified DSH: `0.2.0-rc.1`.** The verified list gains the currently running `0.2.0-rc.1`, and the two load-bearing ranges widen to `<0.3.0`.

### Why this release exists

Since DSH `0.2.0-rc.1`, profile load enforces the peer ranges a bundle declares: if none of its `@deepseek-ai/dsh-*` peer ranges admits the running DSH version, the bundle is skipped without loading and without anything on the page explaining why. This plugin's previous `>=0.1.7-alpha.2 <0.2.0` happened to load on `0.2.0-rc.1` (a prerelease sorts below `0.2.0`, and the load gate includes it), but that was a **time bomb**:

- The day DSH `0.2.0` **stable** ships, `<0.2.0` no longer contains the running release and the plugin is silently dropped.
- This is the mirror image of the `0.1.6`-era lower bound that had to name `0.1.7-alpha.2` explicitly — the same rule, on the upper end this time.

`dsh.engines.dsh` and `peerDependencies['@deepseek-ai/dsh-settings']` therefore widen from `>=0.1.7-alpha.2 <0.2.0` to `>=0.1.7-alpha.2 <0.3.0`, matching the same adaptation already shipped in `@idoall/dsh-notify` 0.4.1.

### Why `0.2.0-rc.1` may be declared verified

Following the repository discipline — verify on a running instance, record, then declare — the evidence has three layers:

- **Live evidence**: the plugin is loaded and running right now in this DSH `0.2.0-rc.1` profile under the `0.1.10` manifest (no skipping warning at profile start; the sidebar chip renders normally).
- **Per-package audit**: every package in `dsh.client.inject` (`dsh-api-remotes`, `dsh-client-connection`, `dsh-client-ui-layout`, `dsh-client-ui-sidebar`, `dsh-client-ui-settings(-general)`) plus the `dsh-settings` peer changed between `dsh-v0.1.7-rc.2` and `dsh-v0.2.0-rc.1` only in versions, bilingual READMEs and tsconfig; the only two source changes are purely additive — mounting the `dsh-client-product-analytics` remote contribution, and telemetry on two sidebar panel clicks. None of the surfaces this plugin uses (`remote.settings`, the `ctx.configForms` channel, the sidebar slots, the authenticated Connection RPC) changed.
- **Locked by tests**: `tests/shared/compatibility.spec.ts` asserts with the repository's own prerelease-aware comparator that both ranges admit every verified release — `<0.3.0` passes for all four.

### What changed

- **Declarations only; zero code.** [`package.json`](../../package.json): version `0.1.11`; `dsh.engines.dsh` and `peerDependencies['@deepseek-ai/dsh-settings']` widen to `>=0.1.7-alpha.2 <0.3.0`; `dsh.compatibility.dshReleases` gains `"0.2.0-rc.1": "compatible"`. `VERIFIED_DSH_VERSIONS` in [`src/shared/types.ts`](../../src/shared/types.ts) adds `0.2.0-rc.1` in lockstep (a test keeps the two lists identical). Both READMEs and the CHANGELOG follow.
- **Unchanged**: the Host half, the status read, the RPC routes, the brand-row chip, the three dot states, the detail panel, the LAN (non-loopback) fallback and the three preference fields — all 118 tests pass. No migration is needed.

### Who is affected, and what to do

- **Running `0.1.10` on DSH `0.2.0-rc.1`**: nothing to do. This release only declares the status quo; after upgrading, the panel reports `0.2.0-rc.1` as **verified** instead of *unverified*.
- **Planning to follow DSH `0.2.0` stable**: upgrade to `0.1.11` (or newer). Staying on `0.1.10` means the plugin is silently dropped the day DSH `0.2.0` ships.
- **Staying on the DSH `0.1.7` line (`rc.2` / `rc.1` / `alpha.2`)**: `0.1.11` declares a superset of `0.1.10` and is a drop-in upgrade; on an older DSH (including `0.1.6-alpha.2`) stay on plugin `0.1.5`.
