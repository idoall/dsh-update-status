**兼容的最新 DSH 版本：`0.1.7-rc.2`**（npm `next` 通道当前指向它）。本版同时覆盖 `0.1.7-rc.1` 与 `0.1.7-alpha.2`。

### 为什么发这个版本

DSH 从 `0.1.7-rc.1` 升到了 `0.1.7-rc.2`。发布前逐包比对了本插件实际绑定的 7 个 DSH 包（rc.1 与 rc.2 各取一份，完整 diff）：差异**全部是增量**，来自 rc.2 新增的快捷键（shortcut）目录在插槽与面板之间的传递——设置插槽上下文新增 `settingsOpen` 与 `settingsShortcut`，侧栏壳上下文新增 `shortcuts`，`SidebarRoot` / `HeaderLeadingControls` 新增 `useShortcuts`，布局服务新增 `panelInfo`，新增 `shortcuts.layout` 语言命名空间与 `shortcut.open` 文案，以及 `dsh-schedule/remote` 的类型再导出。

本插件使用的契约**没有一个被移除，也没有一个改变形状**：`ctx.configForms` 表单面、`remote.settings` 的 `settings.describe` / `settings.mutate`、Connection RPC 的 `/api/dsh-update-status.*` 路由，以及四个插槽（`sidebar.brand.name`、`sidebar.footer.action`、`shell.overlay`、`settings.section`）全部照旧。因此本版**代码零改动**，只把 `0.1.7-rc.2` 纳入已验证清单。

### 改了什么

- **`0.1.7-rc.2` 加入已验证清单。** [`src/shared/types.ts`](../../src/shared/types.ts) 的 `VERIFIED_DSH_VERSIONS` 与 [`package.json`](../../package.json) 的 `dsh.compatibility.dshReleases` 同步新增，`0.1.7-alpha.2` 与 `0.1.7-rc.1` 保留。两处清单一旦漂移，`tests/shared/compatibility.spec.ts` 会直接失败。
- **用户可见的效果：跟随 `next` 通道时不再被标为「尚未验证」。** `0.1.7-rc.2` 发布在 npm 的 `next` 通道上，而旧清单只认到 `0.1.7-rc.1`，所以此前跟随 `next` 的人会看到一条 `preview-unverified` 提示（`notice` 级，从不重绘芯片）。现在运行版本与通道行都显示为**已验证**，该提示消失。升级命令与安装引导文字不受影响，仍原样生成、只供复制。
- **插件版本 `0.1.7` → `0.1.8`。** `dsh.engines.dsh` 与 `peerDependencies['@deepseek-ai/dsh-settings']` 仍为 `>=0.1.7-alpha.2 <0.2.0`，三个已验证版本都在范围内，无需改动；`@deepseek-ai/schemastery` 仍为 peer。
- **零运行时改动。** 宿主半边、客户端半边、RPC 通道、状态读取、侧栏芯片、详情面板、LAN（非回环）回退与偏好设置模型全部未动。

### 谁受影响

- **已经升级到 DSH `0.1.7-rc.2` 的人：本版就是给你的。** 装上后运行版本会被正确标为已验证；不装则只会多一条不重绘芯片的提示，功能不受影响。
- **仍在 `0.1.7-rc.1` 或 `0.1.7-alpha.2` 上的人：本版同样支持**，三个版本都在已验证清单里，可升可不升。
- **从 `0.1.7` 升级：无需任何迁移。** 存储模型、偏好字段、命令生成与 `0.1.7` 完全一致；偏好仍是 profile patch 中 `dsh-update-status` 条目的 `config`。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续使用插件 `0.1.5`。** `0.1.6` 及之后的版本声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`，范围不匹配的 bundle 会在 profile 加载阶段被直接拒绝。

### 兼容性与升级

```sh
dsh plugin --profile web add dsh-update-status@0.1.8
```

宿主半边只在 DSH 启动时加载，所以**需要重启 `dsh web`**；客户端半边刷新页面即生效。本版宿主侧只有版本清单变化，重启后立即生效。

**验证**

- `pnpm run verify`：`tsc --noEmit`（src + tests）、**98/98** vitest、tsdown 构建、`pnpm pack --dry-run`。
- **rc.1 → rc.2 接口核对**：对本插件实际绑定的 7 个 DSH 包（`dsh-settings`、`dsh-client-ui-settings`、`dsh-client-ui-settings-general`、`dsh-client-ui-sidebar`、`dsh-client-ui-layout`、`dsh-client-connection`、`dsh-api-remotes`）逐一 diff `0.1.7-rc.1` 与 `0.1.7-rc.2`，结论如上：只有增量，没有破坏性改动。
- **真机加载检查**：在临时 `DSH_HOME` 中把本仓库以 `link:` 装入 web profile，再执行 `dsh --profile web --dump-config`（DSH `0.1.7-rc.2`），成功组合出 `dsh-update-status` 条目且无任何兼容性拒绝——即 rc.2 的 profile 加载门控接受本 bundle。
- **诚实的边界**：本版**没有**做面板与芯片在 rc.2 上的端到端交互复核（那需要一次真实的 `dsh web` 会话）。rc.2 相对 rc.1 的差异是增量式的快捷键功能，不触及本插件渲染的插槽；`0.1.6` 的真机适配结论继续成立。

### 限制

- **偏好设置属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享；同一实例下多浏览器/设备共享那一份 profile patch 条目。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写这些偏好。
- **非回环页面依赖插件自己的直连通道**：DSH 官方策略是不为非 loopback 页面持久化设置，插件为此额外走一次公开 Remote；若未来 DSH 改动该 Remote 的形状，局域网页面会退回「只读 + 默认值」。
- **芯片依赖 DSH 的侧栏插槽**：`sidebar.brand.name`（单值、最低优先级胜出）、`sidebar.footer.action`、`shell.overlay`、`settings.section`。DSH 大改侧栏或设置面板结构后芯片可能不再显示。
- **只读**：不安装、不重启、不回滚、不下载、不替换任何文件。`canApplyInPlace` 恒为 `false`，升级命令只生成、只供复制。红色芯片只表示「读不出状态」，不会替你做任何决定。
- **改设置后不会自动发请求**：修改缓存时长只在之后普通读取且缓存到期时生效；「检查更新」始终是立即手动检查。

### Why this release exists

DSH moved from `0.1.7-rc.1` to `0.1.7-rc.2`. Before shipping, every DSH package this plugin actually binds to was diffed across the two releases (all 7 of them, full contents): **every difference is additive**, and all of it comes from rc.2's new shortcut catalog being threaded through slots and panels — the settings slot context gains `settingsOpen` and `settingsShortcut`, the sidebar shell context gains `shortcuts`, `SidebarRoot` / `HeaderLeadingControls` gain `useShortcuts`, the layout service gains `panelInfo`, a `shortcuts.layout` locale namespace and a `shortcut.open` label appear, and `dsh-schedule/remote` is re-exported as a type.

**Not one contract this plugin uses was removed or reshaped**: the `ctx.configForms` form face, `remote.settings`' `settings.describe` / `settings.mutate`, the Connection RPC routes `/api/dsh-update-status.*`, and all four slots (`sidebar.brand.name`, `sidebar.footer.action`, `shell.overlay`, `settings.section`). So this release is **zero code change** — it only adds `0.1.7-rc.2` to the verified list.

### What changed

- **`0.1.7-rc.2` joins the verified list.** `VERIFIED_DSH_VERSIONS` in [`src/shared/types.ts`](../../src/shared/types.ts) and `dsh.compatibility.dshReleases` in [`package.json`](../../package.json) both gain it, keeping `0.1.7-alpha.2` and `0.1.7-rc.1`. If the two lists ever drift apart, `tests/shared/compatibility.spec.ts` fails.
- **The user-visible effect: following the `next` channel no longer reads as "not verified".** `0.1.7-rc.2` is what npm's `next` dist-tag publishes, and the old list stopped at `0.1.7-rc.1`, so anyone following `next` saw a `preview-unverified` advisory (`notice` level, never repaints the chip). The running version and the channel row now read **verified**, and that advisory is gone. The upgrade command and installation guidance are untouched — still generated for copying only.
- **Plugin version `0.1.7` → `0.1.8`.** `dsh.engines.dsh` and `peerDependencies['@deepseek-ai/dsh-settings']` stay `>=0.1.7-alpha.2 <0.2.0`, which already admits all three verified releases, and `@deepseek-ai/schemastery` stays a peer.
- **Zero runtime change.** The Host half, the client half, the RPC channel, the status read, the sidebar chip, the detail panel, the LAN (non-loopback) fallback and the preference model are all untouched.

### Who is affected

- **Anyone already on DSH `0.1.7-rc.2`: this release is for you.** Install it and the running version is correctly labelled verified; without it you only get one advisory that never repaints the chip, so nothing breaks either way.
- **Anyone still on `0.1.7-rc.1` or `0.1.7-alpha.2`: this release supports you too** — all three are on the verified list, so upgrading is optional.
- **Upgrading from `0.1.7`: no migration at all.** The storage model, the preference fields and command generation are identical to `0.1.7`; the preferences are still the `config` of the `dsh-update-status` entry in the profile patch.
- **Anyone still on an older DSH (including `0.1.6-alpha.2`): stay on plugin `0.1.5`.** `0.1.6` and later declare `>=0.1.7-alpha.2 <0.2.0`, and a bundle whose range does not match is refused at profile load.

### Compatibility and upgrade

```sh
dsh plugin --profile web add dsh-update-status@0.1.8
```

The Host half loads at DSH startup, so a **restart of `dsh web` is required**; the client half takes effect on a page refresh. This release's only Host-side change is the version list, and it applies as soon as DSH restarts.

**Verification**

- `pnpm run verify`: `tsc --noEmit` (src + tests), **98/98** vitest, tsdown build, `pnpm pack --dry-run`.
- **rc.1 → rc.2 interface audit**: all 7 DSH packages this plugin binds to (`dsh-settings`, `dsh-client-ui-settings`, `dsh-client-ui-settings-general`, `dsh-client-ui-sidebar`, `dsh-client-ui-layout`, `dsh-client-connection`, `dsh-api-remotes`) were diffed between `0.1.7-rc.1` and `0.1.7-rc.2`. The result is above: additive only, nothing breaking.
- **Live load check**: this repository was installed with `link:` into a web profile under a disposable `DSH_HOME`, and `dsh --profile web --dump-config` (DSH `0.1.7-rc.2`) composed the `dsh-update-status` entry with no compatibility refusal — i.e. rc.2's profile-load gate accepts this bundle.
- **An honest boundary**: this release did **not** re-run the end-to-end panel/chip interaction on rc.2 (that needs a real `dsh web` session). The rc.1 → rc.2 delta is additive shortcut plumbing that does not touch the slots this plugin renders, and the `0.1.6` live adaptation conclusion still stands.

### Limitations

- **The preferences belong to a single DSH instance**: two independent DSH servers do not share them; within one instance every browser and device shares the one profile-patch entry.
- **No permission model**: anyone who can reach the profile's authenticated routes can read and write the preferences.
- **Non-loopback pages rely on the plugin's own direct channel**: DSH's stock policy is not to persist settings for a non-loopback page, so the plugin pays one extra public Remote call there. If DSH changes that Remote's shape, LAN pages fall back to "read-only + defaults".
- **The chip depends on DSH's sidebar slots**: `sidebar.brand.name` (single, lowest priority wins), `sidebar.footer.action`, `shell.overlay` and `settings.section`. A large DSH change to the sidebar or the settings panel could make the chip stop rendering.
- **Read-only**: it never installs, restarts, rolls back, downloads or replaces any file. `canApplyInPlace` is always `false`, and the upgrade command is generated for copying only. A red chip only means "the update state could not be read"; it never makes a decision for you.
- **Changing a preference issues no request**: a cache-duration change takes effect only on a later ordinary read once the cache has expired, and **Check for updates** is always an immediate manual check.
