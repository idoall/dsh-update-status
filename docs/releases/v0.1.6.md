<h3 id="cn-v0.1.6">插件 0.1.6 — 已验证 DeepSeek Harness 0.1.7-rc.1 与 0.1.7-alpha.2</h3>

DSH `0.1.7` 移除了本插件赖以工作的两套 API，因此这是一次必需的重写而非增量修补。**`0.1.6` 只支持 DSH `0.1.7` 线**；更早的 DSH（含 `0.1.6-alpha.2`）请继续用 `0.1.5`。

具体来说：宿主侧的 `ctx.settings.register(命名空间, schema, 选项)` 已经不存在——`0.1.7` 的设置服务改为投影每个 Loader 条目自身 `Config` 的 **volatile** 字段，而且**设置表单的命名空间就是条目 id**；客户端侧的 `ctx.settingsScope` 服务同样被移除，继任者是 `ctx.configForms.get(条目id)`。因此在 `0.1.7` 上，`0.1.5` 既读不到也写不了任何一个偏好设置。

### 问题修复

- **宿主半：`settings.register` 已不存在（致命项）。** 原先 `settings.register('dsh-update-status', schema, { base, applies })` 会抛 `register is not a function` 并被容错吞掉，该命名空间从此永远不存在——在 `0.1.7` 上偏好设置必然全灭。现在宿主半直接导出 `Config`（schemastery），其中 `sidebarEnabled`、`channel`、`cacheTtlMinutes` 三个字段标了 `.volatile()`：每次编辑都提交进运行中的引用并发 `loader/volatile-update`，**不会重挂载插件**（否则每改一次开关都会重启状态读取、关掉已打开的面板）。`cacheTtlHours`、`timeoutMs`、`autoCheckOnMount` 三个部署字段保持普通 Config，**不会**出现在表单里，避免表单编辑改写部署配置。
- **命名空间改名：`dsh-update-status` 现在就是 `cordis.patch.yml` 里的 `id`。** 它是存储键，从此不可再改；一个测试直接读取该文件并断言 `id` 与插件常量一致，防止两边漂移后偏好悄悄失去归属。
- **存储位置变更：** 偏好不再写在 `~/.dsh/settings.yaml`，而是作为该条目的 `config` 落在当前 profile 的 `cordis.patch.yml`（`~/.dsh/profiles/<profile>/cordis.patch.yml`）。这是 `0.1.7` 官方的插件偏好模型，写入仍是原子替换并保留 YAML 注释。DSH 会把遗留的 `settings.yaml` 同 id 段落一次性导入到同一条目。
- **客户端半：`ctx.settingsScope` 服务已不存在。** 官方通道改为 `ctx.configForms.get(条目id)`；新增的 `src/client/settings/configFormScope.ts` 把它投影到插件自己的 scope 契约上。`set` 返回 `false`（被拒）会翻译成拒绝，管理界面因此仍能提示冲突，而不会假装写入成功；传输故障同样拒绝。
- **抑制重复的自动表单页。** `Config` 出现后 DSH 会默认为该条目生成一个通用表单，与本插件自带的 `settings.section` 页面重复。按官方惯例（`ui-theme`、`ui-chat`、`ui-conversation` 同样做法）注册 `settings.configure({ auto: false })`；命名空间行本身仍留在 `settings.describe()` 中，读写不受影响。

### 改进

- **`@deepseek-ai/schemastery` 由普通 dependency 改为 peer**（同时保留 devDependency）：DSH `0.1.7` 只从运行安装解析 link 插件的 peer 依赖，普通依赖会在插件自己的 `node_modules` 下查找，而本仓库不提供该目录，`link:` 安装时 Host 半边会 import 失败。
- **兼容性声明修正。** `dsh.engines.dsh` 与 `peerDependencies['@deepseek-ai/dsh-settings']` 都声明 `>=0.1.7-alpha.2 <0.2.0`。下界特意写成这个 alpha：按 node-semver 默认的预发布规则，`>=0.1.6-0 <0.2.0` 这样的范围**并不接纳** `0.1.7-alpha.2`。另补 `dsh.manifestVersion`，并在 `dsh.client.inject` 中补 `@deepseek-ai/dsh-api-remotes`（局域网直连通道直接使用 `remote.settings`）。注意 DSH `0.1.7-rc.1` 会在 profile 加载时**拒绝不兼容的 bundle**，所以这些范围是能否加载的硬条件。
- **测试从 70 条增加到 94 条。** 新增 `tests/host/settings.spec.ts`：锁定 volatile 字段集合（恰好是三个偏好）、表单默认值、`id` 即命名空间的不变量，以及页面策略在 settings 服务缺失或被拒时的容错。`tests/client/settingsChannel.spec.ts` 新增 `configFormScope` 用例：投影、`false`→冲突拒绝、传输异常→不可达拒绝、memory 模式回落直连。`tests/shared/compatibility.spec.ts` 新增：engines 与 peer 范围必须**接纳**每一个已验证版本、schemastery 必须是 peer、客户端 inject 必须包含所用服务。
- **状态读取、RPC 通道、侧栏芯片、详情面板与局域网回落均无行为变化。** `connection.fetch.register` 仍以精确路径提供 `/api/dsh-update-status.*` 路由，浏览器端 `connection.rpc` 面未变，插件使用的插槽契约（`sidebar.brand.name` 单值且最低优先级胜出，`sidebar.footer.action` / `shell.overlay` / `settings.section` 列表）在 `0.1.7` 中仍然一致。

<h3 id="en-v0.1.6">Plugin 0.1.6 — verified against DeepSeek Harness 0.1.7-rc.1 and 0.1.7-alpha.2</h3>

DSH `0.1.7` removed the two APIs this plugin was built on, so this is a required rewrite rather than an incremental fix. **`0.1.6` supports the DSH `0.1.7` line only**; on an older DSH — including `0.1.6-alpha.2` — stay on `0.1.5`.

Concretely: the Host-side `ctx.settings.register(namespace, schema, options)` is gone — `0.1.7`'s settings service projects the **volatile** fields of each active Loader entry's own `Config`, and **a form namespace IS the entry id** — and the client-side `ctx.settingsScope` service is gone too, replaced by `ctx.configForms.get(entryId)`. On `0.1.7`, `0.1.5` could neither read nor write a single preference.

### Bug Fixes

- **Host half: `settings.register` no longer exists (fatal).** The old `settings.register('dsh-update-status', schema, { base, applies })` threw `register is not a function`, the error was swallowed by a guard, and the namespace therefore never existed — on `0.1.7` the preferences were dead. The Host half now exports a `Config` (schemastery) whose `sidebarEnabled`, `channel` and `cacheTtlMinutes` fields are `.volatile()`: an edit commits into the running references and emits one `loader/volatile-update`, so it **never remounts the plugin** (a remount would restart the status read and close an open panel on every toggle). The deployment fields `cacheTtlHours`, `timeoutMs` and `autoCheckOnMount` stay ordinary Config and are **not** projected into the form, so a form edit cannot rewrite deployment configuration.
- **Namespace renamed: `dsh-update-status` is now the `id` in `cordis.patch.yml`.** It is the storage key and must not change; a test reads that file and asserts the `id` matches the plugin constant, so a drift cannot silently detach the preferences.
- **Storage moved.** The preferences no longer live in `~/.dsh/settings.yaml`; they persist as that entry's `config` in the active profile's `cordis.patch.yml` (`~/.dsh/profiles/<profile>/cordis.patch.yml`). That is `0.1.7`'s official plugin-preference model, the write is still an atomic replacement preserving YAML comments, and DSH imports a leftover same-id `settings.yaml` section into the entry once.
- **Client half: the `ctx.settingsScope` service is gone.** The official channel is now `ctx.configForms.get(entryId)`; the new `src/client/settings/configFormScope.ts` projects it onto the plugin's own scope contract. A refused `set` (`false`) becomes a rejection so the settings page still surfaces a conflict instead of pretending the edit landed, and a transport fault rejects too.
- **The duplicate auto-generated settings page is suppressed.** With a `Config` present DSH generates a generic form for the entry, duplicating the plugin's own `settings.section` page. Following the documented convention (`ui-theme`, `ui-chat`, `ui-conversation` all do this), the plugin registers `settings.configure({ auto: false })`; the entry's row stays in `settings.describe()` and reads/writes are unaffected.

### Improvements

- **`@deepseek-ai/schemastery` moved from a plain dependency to a peer** (with a devDependency kept for this repository's own tests): DSH `0.1.7` resolves only a LINKED plugin's peer dependencies from the running installation, so a plain dependency made the Host half fail to import from a `link:` install.
- **Compatibility declarations corrected.** `dsh.engines.dsh` and `peerDependencies['@deepseek-ai/dsh-settings']` both declare `>=0.1.7-alpha.2 <0.2.0`. The lower bound names the alpha on purpose — under node-semver's default prerelease rule a range like `>=0.1.6-0 <0.2.0` does **not** admit `0.1.7-alpha.2`. `dsh.manifestVersion` is declared and `dsh.client.inject` gains `@deepseek-ai/dsh-api-remotes` (the LAN direct channel speaks `remote.settings`). Note that DSH `0.1.7-rc.1` **refuses an incompatible bundle at profile load**, so these ranges decide whether the plugin loads at all.
- **Tests went from 70 to 94.** New `tests/host/settings.spec.ts` locks the volatile field set (exactly the three preferences), the form defaults, the id-is-namespace invariant, and the page policy's tolerance of a missing or refusing settings service. `tests/client/settingsChannel.spec.ts` gains `configFormScope` specs: the projection, `false` → conflict rejection, transport fault → unreachable rejection, and the memory-mode fallback to the direct channel. `tests/shared/compatibility.spec.ts` now also proves the engines and peer ranges ADMIT every verified release, that schemastery is a peer, and that the client inject list carries the services actually used.
- **The status read, the RPC channel, the sidebar chip, the detail panel and the LAN fallback are unchanged.** `connection.fetch.register` still serves the exact `/api/dsh-update-status.*` routes, the browser `connection.rpc` face is unchanged, and the slot contracts the plugin uses (`sidebar.brand.name` single with lowest-priority-wins, `sidebar.footer.action` / `shell.overlay` / `settings.section` lists) still match on `0.1.7`.

### Compatibility and upgrade

- Verified: DeepSeek Harness `0.1.7-rc.1` and `0.1.7-alpha.2`. `0.1.6` **supports the `0.1.7` line only**; on `0.1.6-alpha.2` and older stay on plugin `0.1.5`.
- This version is not on npm yet. Install from the repository (development form):

  ```sh
  pnpm install && pnpm run build
  dsh plugin --profile web add "link:$(pwd)"
  ```

- Once published, the upgrade command is:

  ```sh
  dsh plugin --profile web add dsh-update-status@0.1.6
  ```

- **Storage moves to the profile patch**: if you previously kept a `dsh-update-status` section in `~/.dsh/settings.yaml`, DSH imports it into the same-id entry once after startup and renames the file to `settings.yaml.imported`. If you never used the preferences, no migration is needed.
- **Restart the DSH host** (the Host half loads at startup), then refresh the Web GUI. With `patchReload: live`, a hot-mounted plugin only needs a page refresh.
- The plugin is still **read-only**: it never installs, restarts, rolls back, downloads or replaces any file. A red chip only means "the update state could not be read"; it never makes a decision for you.
