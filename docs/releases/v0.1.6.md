**兼容的最新 DSH 版本：`0.1.7-rc.1`**（`0.1.7` 系列的首个候选版本）。本版同时覆盖 `0.1.7-alpha.2`。

### 为什么必须适配

DSH `0.1.7` 移除了本插件赖以工作的两套 API。这不是增量修补，而是必需的重写：在 `0.1.7` 上，`0.1.5` 既读不到也写不了**任何一个**偏好设置——而这两处失败都是**静默**的，不会在界面上报错。三点都从运行实例的源码与产物核实过，不是猜测：

1. **宿主半：`ctx.settings.register(命名空间, schema, 选项)` 已不存在。** `0.1.7` 的设置服务改为投影每个 Loader 条目**自身 `Config` 的 volatile 字段**，而且**设置表单的命名空间就是条目 id**（`docs/subsystems/settings.md`「Identity and values」）。旧代码的 `settings.register(...)` 抛 `register is not a function`，被外层的容错 `try/catch` 吞掉——于是 `dsh-update-status` 命名空间**从此永远不存在**，侧栏开关、发布通道、缓存时长三项偏好全部失效，且没有任何提示。
2. **客户端半：`ctx.settingsScope` 服务已不存在。** 继任者是 `ctx.configForms.get(条目id)`（`@deepseek-ai/dsh-client-ui-settings`），它共享同一份 `settings.describe` 镜像与官方写入队列。旧代码 `ctx.inject(['settingsScope'], …)` 永远不会被触发，插件于是只能一直停在默认值上。
3. **旧声明在 `0.1.7` 上也不再成立。** `0.1.7` 起，只有 link 插件的 **peer** 依赖会从运行实例解析，普通 `dependencies` 只在插件自己的 `node_modules` 下查找；而 `0.1.7-rc.1` 还会在 **profile 加载时直接拒绝不兼容的 bundle**。因此依赖与范围声明不再是"文档"，而是能否加载的硬条件。

### 改了什么

- **宿主半：偏好设置就是插件条目自己的 volatile `Config`。** `src/host/settings.ts` 不再调用 `settings.register`，改为导出一份 `Config`（schemastery）：
  - 用户偏好 `sidebarEnabled`、`channel`、`cacheTtlMinutes` 全部标 `.volatile()`。每次编辑都提交进运行中的引用并发一次 `loader/volatile-update`，**不会重挂载插件**——否则每改一次开关都会重启状态读取、并关掉已打开的面板。
  - 部署字段 `cacheTtlHours`、`timeoutMs`、`autoCheckOnMount` 保持普通 Config，**不会**出现在表单里，避免表单编辑改写部署配置。
- **命名空间 = `cordis.patch.yml` 的 `id`。** 表单命名空间就是 Loader 条目 id，因此 `dsh-update-status` 从此是**存储键，不可再改**。新增测试直接读取该文件并断言 `id` 与插件常量一致，防止两边漂移后偏好悄悄失去归属。
- **存储位置迁移到 profile patch。** 偏好不再写在 `~/.dsh/settings.yaml`，而是作为该条目的 `config` 落在当前 profile 的 `cordis.patch.yml`（`~/.dsh/profiles/<profile>/cordis.patch.yml`）。这是 `0.1.7` 官方的插件偏好模型，写入仍是原子替换并保留 YAML 注释。DSH 会把遗留的 `settings.yaml` 同 id 段落**一次性导入**到同一条目，随后把该文件改名为 `settings.yaml.imported`。
- **客户端半：官方通道改为 `ctx.configForms.get(条目id)`。** 新增 `src/client/settings/configFormScope.ts`，把官方表单投影到插件自己的 scope 契约上。两处刻意的翻译：
  - `set` 返回 `false`（被拒）→ 抛冲突拒绝，设置页因此仍会提示冲突，而不是假装写入成功；传输故障同样拒绝。
  - `mode` 区分两类页面：非回环页面被固定为 `memory`，表单终态 `unavailable` 且永不写线上——这正是把偏好交给局域网直连通道的条件。
- **抑制重复的自动表单页。** `Config` 出现后 DSH 会默认为该条目生成一个通用表单，与本插件自带的「设置 → 版本与更新」页面重复。按官方惯例（`ui-theme`、`ui-chat`、`ui-conversation` 同样做法）注册 `settings.configure({ auto: false }, ctx.fiber)`；命名空间行本身仍留在 `settings.describe()` 中，读写不受影响。
- **`@deepseek-ai/schemastery` 由普通 dependency 改为 peer**（同时保留 devDependency 供本仓库自测）：`0.1.7` 只从运行安装解析 link 插件的 peer 依赖，否则 `link:` 装入后宿主半边会 import 失败、整个插件加载不起来。
- **兼容性声明修正。** `dsh.engines.dsh` 与 `peerDependencies['@deepseek-ai/dsh-settings']` 都声明 `>=0.1.7-alpha.2 <0.2.0`：
  - 下界特意写成这个 alpha。按 node-semver 默认的预发布规则，`>=0.1.6-0 <0.2.0` 这样的范围**并不接纳** `0.1.7-alpha.2`。
  - 这个范围**同时覆盖** `0.1.7-alpha.2` 与 `0.1.7-rc.1`（只要某个比较符写了同一个 `major.minor.patch`，该版本的预发布就会被接纳）。无需为 RC 放宽范围，也就不会顺带接纳未经测试的版本。
  - 另补 `dsh.manifestVersion`，并在 `dsh.client.inject` 中补 `@deepseek-ai/dsh-api-remotes`（局域网直连通道直接使用 `remote.settings`）。
- **测试从 70 条增加到 94 条。** 新增 `tests/host/settings.spec.ts`：锁定 volatile 字段集合（恰好是那三个偏好）、表单默认值、`id` 即命名空间的不变量，以及页面策略在 settings 服务缺失或被拒时的容错。`tests/client/settingsChannel.spec.ts` 新增 `configFormScope` 用例：投影、`false`→冲突拒绝、传输异常→不可达拒绝、memory 模式回落直连。`tests/shared/compatibility.spec.ts` 新增：engines 与 peer 范围必须**接纳**每一个已验证版本、schemastery 必须是 peer、客户端 inject 必须包含所用服务。

### 谁受影响

- **正在使用 `0.1.7-rc.1` 或 `0.1.7-alpha.2` 的人**：直接升级即可。本版就是为 `0.1.7` 线发布的，也是这两个版本上唯一能让偏好设置真正生效的版本。
- **从 `0.1.5` 升级的人**：**偏好会迁移，不需要手工搬数据**。若你此前在 `~/.dsh/settings.yaml` 里留过 `dsh-update-status` 段，DSH 会在启动后一次性导入到同 id 条目；若你从未用过偏好设置，则无需任何动作。状态读取、侧栏芯片、详情面板、升级命令生成的行为**完全不变**。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续用插件 `0.1.5`。** `0.1.6` 声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`，低于它的版本未经本轮验证；在 `0.1.7-rc.1` 上，范围不匹配的 bundle 会在 profile 加载阶段被直接拒绝。
- **通过局域网转发（`dsh-bridge`、`dsh-lan-proxy`、`dsh-mobile` 等）从手机访问的人**：不受影响。官方表单在非回环页面依旧被固定为 `memory`，插件照旧回落到同一条公开 Remote（`settings.describe` / `settings.mutate`）读写 Host 上那一份共享条目。

### 兼容性与升级

```sh
dsh plugin --profile web add dsh-update-status@0.1.6
```

宿主半边只在 DSH 启动时加载，所以**通常需要重启 `dsh web`**；客户端半边刷新页面即生效。若 profile 开启了 `patchReload: live`（本机 `web` profile 即是），插件热挂载后刷新页面即可——本次验证就是如此完成的，全程没有重启 DSH。

本次在**运行中的 `0.1.7-rc.1` 实例**上实测通过，证据来自运行实例本身而不是推断：

1. `link:` 装入后插件热挂载：宿主把条目组合进 profile，Web 端正常下发 `dsh-update-status/client.js`。
2. 侧栏芯片渲染出**正在运行的版本 `0.1.7-rc.1`**，说明 `POST /api/dsh-update-status.get-status` 已认证并返回 200——Host 半的 RPC 路由在 RC 上完好。
3. `POST /api/settings/describe` 返回 200，说明官方设置镜像包含本条目。
4. 插件自带的「设置 → 版本与更新」分区正常渲染，且**控件可写**（开关与通道选择均非 disabled），自动生成的通用表单页已被抑制。
5. 切换侧栏开关后，`config: {sidebarEnabled: false}` 真的写进了 `~/.dsh/profiles/web/cordis.patch.yml`——完整的"客户端 → configForms → settings.mutate → configEditor → profile patch"写入链路在 RC 上打通。

`pnpm run verify`（`tsc --noEmit` + 94/94 vitest + `tsdown` 构建 + `pnpm pack --dry-run`）全绿。

### 限制

- **偏好设置属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享；同一实例下多浏览器/设备共享那一份 profile patch 条目。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写这些偏好。
- **非回环页面依赖插件自己的直连通道**：DSH 官方策略是不为非 loopback 页面持久化设置，插件为此额外走一次公开 Remote；若未来 DSH 改动该 Remote 的形状，局域网页面会退回"只读 + 默认值"。
- **芯片依赖 DSH 的侧栏插槽**：`sidebar.brand.name`（单值、最低优先级胜出）、`sidebar.footer.action`、`shell.overlay`、`settings.section`。DSH 大改侧栏或设置面板结构后芯片可能不再显示。
- **只读**：不安装、不重启、不回滚、不下载、不替换任何文件。`canApplyInPlace` 恒为 `false`，升级命令只生成、只供复制。红色芯片只表示"读不出状态"，不会替你做任何决定。
- **改设置后不会自动发请求**：修改缓存时长只在之后普通读取且缓存到期时生效；「检查更新」始终是立即手动检查。

### Why an adaptation was required

DSH `0.1.7` removed the two APIs this plugin was built on. This is a required
rewrite rather than an incremental fix: on `0.1.7`, `0.1.5` could neither read
nor write **a single** preference — and both failures were **silent**, with no
error surfaced in the UI. All three points were checked against the running
instance's own source and shipped artifacts, not inferred:

1. **Host half: `ctx.settings.register(namespace, schema, options)` is gone.**
   `0.1.7`'s settings service projects the **volatile fields of each Loader
   entry's own `Config`**, and **a form namespace IS the entry id**
   (`docs/subsystems/settings.md`, "Identity and values"). The old
   `settings.register(...)` threw `register is not a function`, the guard's
   `try/catch` swallowed it, and the `dsh-update-status` namespace therefore
   **never existed** — the sidebar toggle, the followed channel and the cache
   duration were all dead, with nothing shown to the user.
2. **Client half: the `ctx.settingsScope` service is gone.** Its successor is
   `ctx.configForms.get(entryId)` (`@deepseek-ai/dsh-client-ui-settings`), which
   shares the same `settings.describe` mirror and the same official write queue.
   The old `ctx.inject(['settingsScope'], …)` never ran, so the plugin could only
   ever sit on its defaults.
3. **The old declarations no longer hold on `0.1.7` either.** From `0.1.7`, only
   a linked plugin's **peer** dependencies resolve from the running
   installation; a plain `dependency` is looked up under the plugin's own
   `node_modules`. And `0.1.7-rc.1` **refuses an incompatible bundle at profile
   load**. Dependency and range declarations are therefore load-bearing, not
   documentation.

### What changed

- **Host half: the preferences ARE the plugin entry's own volatile `Config`.**
  `src/host/settings.ts` no longer calls `settings.register`; it exports one
  `Config` (schemastery):
  - The user preferences `sidebarEnabled`, `channel` and `cacheTtlMinutes` are
    all `.volatile()`. Every edit commits into the running references and emits
    one `loader/volatile-update`, so it **never remounts the plugin** — a
    remount would restart the status read and close an open panel on every
    toggle.
  - The deployment fields `cacheTtlHours`, `timeoutMs` and `autoCheckOnMount`
    stay ordinary Config and are **not** projected into the form, so a form edit
    cannot rewrite deployment configuration.
- **The namespace is the `id` in `cordis.patch.yml`.** A form namespace is the
  Loader entry id, so `dsh-update-status` is now a **storage key and must not
  change**. A new test reads that file and asserts the `id` matches the plugin
  constant, so a drift cannot silently detach the preferences.
- **Storage moved to the profile patch.** The preferences no longer live in
  `~/.dsh/settings.yaml`; they persist as that entry's `config` in the active
  profile's `cordis.patch.yml`
  (`~/.dsh/profiles/<profile>/cordis.patch.yml`). That is `0.1.7`'s official
  plugin-preference model, the write is still an atomic replacement preserving
  YAML comments, and DSH **imports a leftover same-id `settings.yaml` section
  once** and then renames the file to `settings.yaml.imported`.
- **Client half: the official channel is now `ctx.configForms.get(entryId)`.**
  The new `src/client/settings/configFormScope.ts` projects the official form
  onto the plugin's own scope contract, with two deliberate translations:
  - A refused `set` (`false`) throws a conflict rejection, so the settings page
    still surfaces a conflict instead of pretending the edit landed; a transport
    fault rejects too.
  - `mode` separates the two page kinds: a non-loopback page is pinned to
    `memory`, where the form is terminally `unavailable` and never crosses the
    wire — exactly the state that hands the preferences to the LAN direct
    channel.
- **The duplicate auto-generated settings page is suppressed.** With a `Config`
  present DSH generates a generic form for the entry, duplicating the plugin's
  own "Settings → Version & updates" page. Following the documented convention
  (`ui-theme`, `ui-chat`, `ui-conversation` all do this), the plugin registers
  `settings.configure({ auto: false }, ctx.fiber)`; the entry's row stays in
  `settings.describe()` and reads/writes are unaffected.
- **`@deepseek-ai/schemastery` moved from a plain dependency to a peer** (with a
  devDependency kept for this repository's own tests): `0.1.7` resolves only a
  linked plugin's peer dependencies from the running installation, so a plain
  dependency made the Host half fail to import from a `link:` install and the
  plugin never loaded.
- **Compatibility declarations corrected.** `dsh.engines.dsh` and
  `peerDependencies['@deepseek-ai/dsh-settings']` both declare
  `>=0.1.7-alpha.2 <0.2.0`:
  - The lower bound names the alpha on purpose. Under node-semver's default
    prerelease rule, a range like `>=0.1.6-0 <0.2.0` does **not** admit
    `0.1.7-alpha.2`.
  - That one range **covers both** `0.1.7-alpha.2` and `0.1.7-rc.1` (a
    prerelease is admitted when some comparator names the same
    `major.minor.patch`). No need to widen it for the RC, so it does not
    silently admit untested versions.
  - `dsh.manifestVersion` is declared, and `dsh.client.inject` gains
    `@deepseek-ai/dsh-api-remotes` (the LAN direct channel speaks
    `remote.settings`).
- **Tests went from 70 to 94.** New `tests/host/settings.spec.ts` locks the
  volatile field set (exactly those three preferences), the form defaults, the
  id-is-namespace invariant, and the page policy's tolerance of a missing or
  refusing settings service. `tests/client/settingsChannel.spec.ts` gains
  `configFormScope` specs: the projection, `false` → conflict rejection,
  transport fault → unreachable rejection, and the memory-mode fallback to the
  direct channel. `tests/shared/compatibility.spec.ts` now also proves the
  engines and peer ranges **admit** every verified release, that schemastery is
  a peer, and that the client inject list carries the services actually used.

### Who is affected

- **Anyone on `0.1.7-rc.1` or `0.1.7-alpha.2`**: upgrade directly. This release
  exists for the `0.1.7` line, and it is the only version whose preferences
  actually work there.
- **Anyone upgrading from `0.1.5`**: **the preferences migrate; no manual data
  work.** If you previously kept a `dsh-update-status` section in
  `~/.dsh/settings.yaml`, DSH imports it into the same-id entry once after
  startup. If you never used the preferences, nothing is required. The status
  read, the sidebar chip, the detail panel and the generated upgrade command are
  **unchanged**.
- **Anyone still on an older DSH (including `0.1.6-alpha.2`): stay on plugin
  `0.1.5`.** `0.1.6` declares `>=0.1.7-alpha.2 <0.2.0`, and on `0.1.7-rc.1` a
  bundle whose range does not match is refused at profile load.
- **Anyone reaching the GUI through a LAN bridge** (`dsh-bridge`,
  `dsh-lan-proxy`, `dsh-mobile`, …): unaffected. The official form is still
  pinned to `memory` on a non-loopback page, and the plugin still falls back to
  the same public Remote (`settings.describe` / `settings.mutate`) to read and
  write the one shared Host entry.

### Limitations

- **The preferences belong to a single DSH instance**: two independent DSH
  servers do not share them; within one instance every browser and device shares
  the one profile-patch entry.
- **No permission model**: anyone who can reach the profile's authenticated
  routes can read and write the preferences.
- **Non-loopback pages rely on the plugin's own direct channel**: DSH's stock
  policy is not to persist settings for a non-loopback page, so the plugin pays
  one extra public Remote call there. If DSH changes that Remote's shape, LAN
  pages fall back to "read-only + defaults".
- **The chip depends on DSH's sidebar slots**: `sidebar.brand.name` (single,
  lowest priority wins), `sidebar.footer.action`, `shell.overlay` and
  `settings.section`. A large DSH change to the sidebar or the settings panel
  could make the chip stop rendering.
- **Read-only**: it never installs, restarts, rolls back, downloads or replaces
  any file. `canApplyInPlace` is always `false`, and the upgrade command is
  generated for copying only. A red chip only means "the update state could not
  be read"; it never makes a decision for you.
- **Changing a preference issues no request**: a cache-duration change takes
  effect only on a later ordinary read once the cache has expired, and **Check
  for updates** is always an immediate manual check.
