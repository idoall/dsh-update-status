<h3 id="cn-v0.1.3">插件 0.1.3 — 已验证 DeepSeek Harness 0.1.6-alpha.1</h3>

本版本修复了**局域网（非回环）页面整个插件失效**的问题，并在 DeepSeek Harness `0.1.6-alpha.1` 上重新验证。因为 `0.1.2` 从未发布到 npm，从 npm 升级的用户会直接从 `0.1.1` 跳到 `0.1.3`，因此下面同时说明这两个版本的全部改动。

### 版本对应

| 插件版本 | 已验证 DeepSeek Harness | npm 发布状态 | 该版本是什么 |
| --- | --- | --- | --- |
| **`0.1.3`** | `0.1.6-alpha.1`、`0.1.5-rc.1` | 本次发布（`latest`） | 含 `0.1.2` 的局域网修复，并在 0.1.6 上复验、补上回归测试 |
| `0.1.2` | `0.1.5-rc.1` | **未发布** | 移除 `connection.isLoopback` 门控，局域网页面可用 |
| `0.1.1` | `0.1.5-rc.1` | 已发布 | 此前 npm 上的 `latest`；局域网/非回环页面下插件整体不可用 |
| `0.1.0` | `0.1.2-rc.1` | 已发布 | 首个版本 |

### 问题修复

- **局域网页面侧栏入口点击无反应、弹窗打不开**：客户端半边把整个功能压在 `connection.isLoopback === true` 上。经 `dsh-bridge` 等转发打开的页面主机名不是 `localhost` / `127.0.0.1`，该判断恒为 false，于是插件从不发送 `POST /api/dsh-update-status.get-status`，详情面板被同一标志位禁用，点击版本胶囊没有任何反应。现在该门控已移除：Connection RPC 本身是已认证的，Host 路由也是本插件自己的路由，状态从任何页面都能读取；页面确实没有可用通道时给出真实错误，而不是编造一个版本号。
- **局域网页面显示的不是当前运行版本**：同一个门控导致版本胶囊退回显示本包在 `package.json` 中声明的兼容版本（`0.1.5-rc.1`），看起来像"没读到最新版本"。修复后显示的是 Host 实际运行版本（如 `0.1.6-alpha.1`）。
- **局域网页面偏好设置全部回落到默认值**：DSH 对非回环页面停用 Host 设置持久化（官方 `dsh-client-ui-settings`：`persistence = ctx.remote.$host.isLoopback ? "host" : "memory"`），`settingsScope` 直接返回 `unavailable` 且从不发送 `settings.describe`，于是 `sidebarEnabled`、`channel`、`cacheTtlMinutes` 全部读不到 Host 上已配置的值——跟随的发布通道会被静默切回 `latest`。现在仅在官方 scope 报 `unavailable` 时，才通过官方同一个公开 Remote（`settings.describe` / `settings.mutate`）打开一条直连 Host 的通道，一份 `dsh-update-status` 命名空间继续服务所有设备。
- **设置写入被拒时不再假装成功**：直连通道按发出顺序串行写入，用命名空间 revision 做栅栏，Host 拒绝时抛出带 Host 错误码的异常并重新读取，而不是静默覆盖。

### 改进

- **在 DeepSeek Harness `0.1.6-alpha.1` 上重新验证**：逐项核对了 0.1.6 的真实接口——`connection.fetch.register` 仍然在共享 Typert 拦截器之前处理 `/api/dsh-update-status.*` 精确路由；浏览器侧 `connection.rpc` 面未变；插件使用的槽位契约（`sidebar.brand.name` 单槽、优先级最低者渲染，`sidebar.footer.action` / `shell.overlay` / `settings.section` 列表槽）与 0.1.6 一致；`settingsScope.bind()` 的 `getSnapshot/subscribe/set` 快照形状与 `remote.$on('settings/document-updated')` 失效事件均未变。
- **兼容性改为"已验证版本清单"**：由单一版本常量改为 `VERIFIED_DSH_VERSIONS`，`0.1.5-rc.1` 与 `0.1.6-alpha.1` 标记为「已验证兼容」，其余版本一律保持「尚未验证兼容」——插件不替没验证过的版本背书。`package.json` 的 `dsh.compatibility.dshReleases` 同步声明这两个版本。
- **新增回归测试** `tests/client/entry.spec.ts`：用真实客户端入口加上结构化的 Cordis 上下文，断言非回环页面必须发出 Host 状态读取、版本胶囊保持遮蔽官方字标的优先级、生命周期副作用只有一处且能完整释放。把 loopback 门控加回去，5 个用例中会有 4 个失败。
- 回环（`localhost` / `127.0.0.1`）页面行为不变：仍走官方 `settingsScope`，不会多发一次线上读取。

### 兼容性与升级

- 已验证：DeepSeek Harness `0.1.6-alpha.1`、`0.1.5-rc.1`。
- 升级插件（先升级 DSH 再升级插件均可）：

  ```sh
  dsh plugin --profile web add dsh-update-status@latest
  ```

- 仍在 DSH `0.1.2-rc.1` 上时请继续使用 `0.1.0`。
- 本插件仍然**只读**：不安装、不重启、不回滚、不下载、不替换任何文件，只显示状态并生成"仅复制"的升级命令。
- 若你希望保持 DSH 官方策略（非回环页面完全不落地设置），可让转发侧声明宿主身份：在返回 HTML 的 `__DSH_BOOT__` 之前注入 `window.__DSH_TRANSPORT__ = { fetch: (input, init) => window.fetch(input, init), ownsHost: true }`，此后 `ctx.connection.isLoopback` 为真，所有依赖设置的界面（含官方设置页）一并恢复。采用本版本后这不再是本插件可用的前提。

<h3 id="en-v0.1.3">Plugin 0.1.3 — verified against DeepSeek Harness 0.1.6-alpha.1</h3>

This release fixes the plugin being **completely inert on LAN (non-loopback) pages** and re-verifies it against DeepSeek Harness `0.1.6-alpha.1`. Because `0.1.2` was never published to npm, anyone upgrading from npm jumps straight from `0.1.1` to `0.1.3`, so both versions' changes are listed below.

### Version matrix

| Plugin | Verified DeepSeek Harness | On npm | What that version is |
| --- | --- | --- | --- |
| **`0.1.3`** | `0.1.6-alpha.1`, `0.1.5-rc.1` | this release (`latest`) | Carries the `0.1.2` LAN fix, re-verified on 0.1.6 and locked by tests |
| `0.1.2` | `0.1.5-rc.1` | **never published** | Removed the `connection.isLoopback` gate; LAN pages work |
| `0.1.1` | `0.1.5-rc.1` | published | The previous npm `latest`; the whole plugin is inert on LAN/non-loopback pages |
| `0.1.0` | `0.1.2-rc.1` | published | First release |

### Bug Fixes

- **Clicking the sidebar entry did nothing and the panel never opened on a LAN page.** The client half gated the entire feature on `connection.isLoopback === true`. A page reached through a forwarder such as `dsh-bridge` has a hostname that is neither `localhost` nor `127.0.0.1`, so the flag is always false there: the plugin never sent `POST /api/dsh-update-status.get-status`, the detail panel was disabled by the same flag, and clicking the version chip had no effect at all. The gate is gone — the Connection RPC is authenticated and the Host route belongs to this plugin, so the read-only status is fetched from whichever page the operator is on, and a page with no usable transport reports an honest error instead of inventing a version.
- **The chip showed something other than the running version on a LAN page.** The same gate made it fall back to the compatible release this bundle declares in `package.json` (`0.1.5-rc.1`), which looks like "it does not read the newest version". It now shows the Host's actual running version (for example `0.1.6-alpha.1`).
- **Every preference silently fell back to its default on a LAN page.** DSH disables Host settings persistence for non-loopback pages (official `dsh-client-ui-settings`: `persistence = ctx.remote.$host.isLoopback ? "host" : "memory"`), so `settingsScope` answers `unavailable` immediately and never sends `settings.describe`. `sidebarEnabled`, `channel` and `cacheTtlMinutes` therefore could not see the values configured on the Host — the followed release channel silently switched back to `latest`. The plugin now opens a direct Host channel over the same public Remote the official settings client speaks (`settings.describe` / `settings.mutate`), but only when the official scope reports `unavailable`, so the one `dsh-update-status` namespace keeps serving every device.
- **A refused settings write no longer pretends to have landed.** The direct channel serializes writes in issue order, fences them by the namespace revision, and rejects with the Host's own error code after a recovery read instead of overwriting silently.

### Improvements

- **Re-verified against DeepSeek Harness `0.1.6-alpha.1`.** The real 0.1.6 interfaces were checked one by one: `connection.fetch.register` still serves exact `/api/dsh-update-status.*` routes ahead of the shared Typert interceptor; the browser `connection.rpc` face is unchanged; the slot contracts the plugin uses (`sidebar.brand.name` single with lowest-priority-wins, plus the `sidebar.footer.action` / `shell.overlay` / `settings.section` lists) still match; and `settingsScope.bind()`'s `getSnapshot`/`subscribe`/`set` snapshot shape together with the `remote.$on('settings/document-updated')` invalidation are unchanged.
- **Compatibility is now a verified-release list.** The single-version constant became `VERIFIED_DSH_VERSIONS`: `0.1.5-rc.1` and `0.1.6-alpha.1` are labelled *verified*, and every other release stays *unverified* — the plugin does not vouch for a version nobody tested. `package.json`'s `dsh.compatibility.dshReleases` declares the same two releases.
- **New regression test** `tests/client/entry.spec.ts` drives the real client entry through a structural Cordis context and asserts that a non-loopback page must issue the Host status read, that the chip keeps its shadowing priority over the official wordmark, and that exactly one lifecycle effect owns teardown. Re-adding the loopback gate fails 4 of its 5 cases.
- Loopback (`localhost` / `127.0.0.1`) pages are unchanged: they keep the official `settingsScope` and pay no extra wire read.

### Compatibility and upgrade

- Verified: DeepSeek Harness `0.1.6-alpha.1` and `0.1.5-rc.1`.
- Upgrade the plugin (upgrading DSH first or the plugin first both work):

  ```sh
  dsh plugin --profile web add dsh-update-status@latest
  ```

- Stay on `0.1.0` while you are still on DSH `0.1.2-rc.1`.
- The plugin remains **read-only**: it never installs, restarts, rolls back, downloads, or replaces files. It only shows status and generates copy-only upgrade commands.
- If you prefer DSH's stock policy (a non-loopback page never persists settings), let the forwarder declare itself the Host by injecting `window.__DSH_TRANSPORT__ = { fetch: (input, init) => window.fetch(input, init), ownsHost: true }` into the served HTML before `__DSH_BOOT__`; `ctx.connection.isLoopback` then reads true and every settings-backed surface, including the official Settings pages, comes back. With this release that is no longer a prerequisite for this plugin.
