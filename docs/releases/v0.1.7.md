**兼容的最新 DSH 版本：`0.1.7-rc.1`**（`0.1.7` 系列的首个候选版本）。本版同时覆盖 `0.1.7-alpha.2`。

### 为什么发这个版本

`0.1.6` 解决的是**「在 DSH 0.1.7 上能不能用」**——`0.1.7` 移除了宿主 `ctx.settings.register(...)` 与客户端 `ctx.settingsScope`，`0.1.5` 在那条线上连一个偏好设置都读写不了。

`0.1.7` 解决的是**「说不说人话」**：运行期告警文本此前由**宿主**直接拼成中文（`无法检查 npm registry：…`、`npm registry 未发布 alpha 通道。`……），而客户端只负责原样显示。于是**英文界面里会冒出中文**——一个纯英文的用户看到的是中文告警。本版把「事实」和「措辞」分开：宿主只输出语言中立的告警代码与插值数据，措辞交给客户端按当前语言渲染。

这一改动来自社区贡献（[@ivkiwi](https://github.com/ivkiwi) 的 PR #7），经复核后 rebase 到 `0.1.6` 之上合入，**原作者署名保留**（commit `362d83e`）。

### 改了什么

- **宿主不再拼措辞。** `UpdateStatus` 新增 `warnings: UpdateWarning[]`，四种语言中立的代码各带自己的插值数据：
  - `registry-unavailable`（`detail`）
  - `channel-unavailable`（`channel`）
  - `version-incomparable`（`currentVersion`、`channel`、`selectedVersion`）
  - `preview-unverified`（`channel`、`version`）

  同时**保留英文 `warning` 字符串**作为混合版本过渡期的兜底：新客户端配旧宿主、或旧客户端配新宿主，都还能显示一句有用的英文，而不是空白。
- **`warningKind` 契约不变。** 仍然按 `0.1.5` 引入的规则推导：全部是 `preview-unverified` → `notice`（提示性，**绝不重绘芯片**），只要有一条是别的 → `failure`（重绘为红色）。所以「DSH 升级快于插件」不会再把芯片涂红。
- **客户端在边界校验载荷。** 新增 `warningOf` 守卫，逐字段验证 `warnings` 的代码与插值类型，畸形载荷被丢弃而不是渲染成 `[object Object]`；随后用客户端自己的 `en` / `zh` 字典渲染，支持 `{param}` 插值。载荷缺失时回退到宿主的英文 `warning`。
- **非命令式安装引导同样本地化。** `source-checkout` 与未知安装方式的两句引导改由客户端渲染（`guidance.sourceCheckout` / `guidance.unknownInstall`）；**真实的升级命令（`npm install -g …` / `pnpm add -g …`）原样透传，不参与本地化**，避免把命令改坏。
- **dev 工具链升级**：tsdown `0.22.14` → `0.23.0`、vitest `4.1.11` → `5.0.1`。**仅开发依赖**，已发布产物不含它们，对使用者没有任何影响。

### 谁受影响

- **使用英文界面的人：本版就是给你的。** 升级前，任何一条运行期告警（registry 读取失败、通道未发布、版本无法比较、预览版未验证）都会以中文出现在英文界面里；现在按界面语言正确显示。
- **使用中文界面的人：措辞与行为都不变。** 中文文案逐字保持原样（例如 `alpha 是预览通道，版本 0.1.7-alpha.2 尚未验证与本插件兼容。`）。
- **从 `0.1.6` 升级：无需任何迁移。** 存储模型完全一致——偏好仍是 profile patch 中 `dsh-update-status` 条目的 `config`，`0.1.6` 写下的值原样继续生效。
- **从 `0.1.5` 或更早升级：** `0.1.6` 的迁移说明仍然适用：若 `~/.dsh/settings.yaml` 里留有 `dsh-update-status` 段，DSH 会一次性导入同 id 条目，然后把该文件改名为 `settings.yaml.imported`。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续用插件 `0.1.5`。** `0.1.7` 声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`；在 `0.1.7-rc.1` 上，范围不匹配的 bundle 会在 profile 加载阶段被直接拒绝。

### 兼容性与升级

```sh
dsh plugin --profile web add dsh-update-status@0.1.7
```

宿主半边只在 DSH 启动时加载，所以**需要重启 `dsh web`**；客户端半边刷新页面即生效。若 profile 开启了 `patchReload: live`，热挂载后刷新页面即可，但本版的宿主侧改动（告警结构）必须重启才会生效。

**验证**

- `pnpm run verify`：`tsc --noEmit`（src + tests）、**98/98** vitest（vitest 5.0.1）、tsdown 0.23.0 构建、`pnpm pack --dry-run`。
- 本地化新增 4 条专门用例：结构化告警的英文渲染、中文渲染、**优先结构化告警并对旧宿主回退**、安装引导本地化且**真实命令原样透传**。
- `0.1.6` 的适配（volatile `Config` 表单、`ctx.configForms` 通道、profile patch 存储）未改动，其真机验证结论继续成立。
- **诚实的边界**：本地化的**实机端到端**验证需要宿主半边重启（只有新宿主才会输出 `warnings` 代码）；本版在 DSH `0.1.7` 上的验证以单元测试为准，作者此前在 `0.1.6-alpha.2` 上做过实机验证。

### 限制

- **偏好设置属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享；同一实例下多浏览器/设备共享那一份 profile patch 条目。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写这些偏好。
- **非回环页面依赖插件自己的直连通道**：DSH 官方策略是不为非 loopback 页面持久化设置，插件为此额外走一次公开 Remote；若未来 DSH 改动该 Remote 的形状，局域网页面会退回「只读 + 默认值」。
- **芯片依赖 DSH 的侧栏插槽**：`sidebar.brand.name`（单值、最低优先级胜出）、`sidebar.footer.action`、`shell.overlay`、`settings.section`。DSH 大改侧栏或设置面板结构后芯片可能不再显示。
- **只读**：不安装、不重启、不回滚、不下载、不替换任何文件。`canApplyInPlace` 恒为 `false`，升级命令只生成、只供复制。红色芯片只表示「读不出状态」，不会替你做任何决定。
- **改设置后不会自动发请求**：修改缓存时长只在之后普通读取且缓存到期时生效；「检查更新」始终是立即手动检查。

**Latest compatible DSH release: `0.1.7-rc.1`** (the first release candidate on the `0.1.7` line). This release also covers `0.1.7-alpha.2`.

### Why this release exists

`0.1.6` was about **whether the plugin works at all** on DSH 0.1.7 — that release removed the Host's `ctx.settings.register(...)` and the Client's `ctx.settingsScope`, and on that line `0.1.5` could not read or write a single preference.

`0.1.7` is about **whether it speaks your language**. Runtime warnings used to be assembled as Chinese sentences by the **Host** (`无法检查 npm registry：…`, `npm registry 未发布 alpha 通道。`, …), and the Client simply displayed that string verbatim. The result: **Chinese text inside an English UI** — a purely English user saw Chinese warnings. This release separates the *fact* from the *wording*: the Host emits language-neutral warning codes plus interpolation data, and the wording is rendered by the Client in the page's own language.

The change comes from a community contribution (PR #7 by [@ivkiwi](https://github.com/ivkiwi)), rebased onto `0.1.6` and landed after review, with **the original authorship preserved** (commit `362d83e`).

### What changed

- **The Host no longer composes sentences.** `UpdateStatus` gains `warnings: UpdateWarning[]` with four language-neutral codes, each carrying its own interpolation data:
  - `registry-unavailable` (`detail`)
  - `channel-unavailable` (`channel`)
  - `version-incomparable` (`currentVersion`, `channel`, `selectedVersion`)
  - `preview-unverified` (`channel`, `version`)

  The English `warning` string is **kept as a mixed-version fallback**: a new client against an older Host — or an older client against a new Host — still shows a useful English sentence instead of nothing.
- **The `warningKind` contract is unchanged.** It is still derived by the rule introduced in `0.1.5`: all `preview-unverified` → `notice` (advisory, **never repaints the chip**); anything else → `failure` (repaints red). So "DSH upgraded ahead of the plugin" still cannot paint the chip red.
- **The Client validates the payload at the boundary.** A new `warningOf` guard checks each code and its interpolation types field by field, so a malformed payload is dropped rather than rendered as `[object Object]`; the warnings are then rendered from the Client's own `en` / `zh` dictionary with `{param}` interpolation. When the field is absent, it falls back to the Host's English `warning`.
- **Non-command installation guidance is localized too.** The two `source-checkout` / unknown-install sentences now render on the Client (`guidance.sourceCheckout` / `guidance.unknownInstall`); **real upgrade commands (`npm install -g …` / `pnpm add -g …`) pass through untouched** and are never localized, so a command can never be corrupted by translation.
- **Dev toolchain bump**: tsdown `0.22.14` → `0.23.0`, vitest `4.1.11` → `5.0.1`. **Development dependencies only** — they are not in the published artifact and have no effect for users.

### Who is affected

- **Anyone using the English UI: this release is for you.** Before it, every runtime warning (registry read failed, channel unpublished, versions not comparable, preview not verified) appeared in Chinese inside the English UI; it now follows the UI language.
- **Anyone using the Chinese UI: wording and behaviour are unchanged.** The Chinese strings are preserved verbatim (for example `alpha 是预览通道，版本 0.1.7-alpha.2 尚未验证与本插件兼容。`).
- **Upgrading from `0.1.6`: no migration at all.** The storage model is identical — the preferences are still the `config` of the `dsh-update-status` entry in the profile patch, and values written by `0.1.6` keep working as-is.
- **Upgrading from `0.1.5` or earlier:** the `0.1.6` migration note still applies. If a `dsh-update-status` section is left in `~/.dsh/settings.yaml`, DSH imports it into the same-id entry once and renames the file to `settings.yaml.imported`.
- **Anyone still on an older DSH (including `0.1.6-alpha.2`): stay on plugin `0.1.5`.** `0.1.7` declares `>=0.1.7-alpha.2 <0.2.0`, and on `0.1.7-rc.1` a bundle whose range does not match is refused at profile load.

### Compatibility and upgrade

```sh
dsh plugin --profile web add dsh-update-status@0.1.7
```

The Host half loads at DSH startup, so a **restart of `dsh web` is required**; the client half takes effect on a page refresh. With `patchReload: live` a hot-mounted plugin only needs a page refresh, but this release's Host-side change (the warning structure) needs the restart to take effect.

**Verification**

- `pnpm run verify`: `tsc --noEmit` (src + tests), **98/98** vitest on vitest 5.0.1, tsdown 0.23.0 build, `pnpm pack --dry-run`.
- Four dedicated specs cover the localization: English rendering of structured warnings, Chinese rendering, **structured warnings preferred with a fallback for an older Host**, and installation guidance localized while **real commands pass through unchanged**.
- The `0.1.6` adaptation (volatile `Config` form, `ctx.configForms` channel, profile-patch storage) is untouched, so its live verification still stands.
- **An honest boundary**: the localization's **end-to-end live** check requires the Host half to be restarted (only a new Host emits `warnings` codes). On DSH `0.1.7` this release is verified by unit tests; the author verified it live on `0.1.6-alpha.2`.

### Limitations

- **The preferences belong to a single DSH instance**: two independent DSH servers do not share them; within one instance every browser and device shares the one profile-patch entry.
- **No permission model**: anyone who can reach the profile's authenticated routes can read and write the preferences.
- **Non-loopback pages rely on the plugin's own direct channel**: DSH's stock policy is not to persist settings for a non-loopback page, so the plugin pays one extra public Remote call there. If DSH changes that Remote's shape, LAN pages fall back to "read-only + defaults".
- **The chip depends on DSH's sidebar slots**: `sidebar.brand.name` (single, lowest priority wins), `sidebar.footer.action`, `shell.overlay` and `settings.section`. A large DSH change to the sidebar or the settings panel could make the chip stop rendering.
- **Read-only**: it never installs, restarts, rolls back, downloads or replaces any file. `canApplyInPlace` is always `false`, and the upgrade command is generated for copying only. A red chip only means "the update state could not be read"; it never makes a decision for you.
- **Changing a preference issues no request**: a cache-duration change takes effect only on a later ordinary read once the cache has expired, and **Check for updates** is always an immediate manual check.
