<h3 id="cn-v0.5.3">插件 0.5.3 — 按 DSH 0.2.2-rc.5 复核，并把「最新构建」这种会过期的写法去掉</h3>

### 版本对应

| 插件 | 该版本是什么 | npm |
| --- | --- | --- |
| `0.5.3` | 按 DSH `0.2.2-rc.5`（现为 npm 的 `latest`）复核：插件代码无改动；安装要求改成不随 DSH 发版过期的写法 | 本次发布，`latest` |
| `0.5.2` | 上一次发布：按 DSH `0.2.2-rc.4` 复核，同样无功能改动 | 已发布 |

### 本版做了什么

- **唯一新增的升级指南条目与本插件无关。** 从 `0.2.2-rc.4` 到 `0.2.2-rc.5` 只多了 `v0.2.2-rc.4` 一个目录，其中仅一条 `web-search-deepseek-model-default`：说明 DSH 在 DeepSeek 模型路由上默认改用旧版 Messages 搜索。本插件不注册搜索/抓取提供方，也不读 `web.*` 配置，因此不涉及。
- **注入的客户端接口没有变化。** 对比本插件注入的七个包（`dsh-settings`、`dsh-api-remotes`、`dsh-client-connection`、`dsh-client-ui-layout`、`dsh-client-ui-sidebar`、`dsh-client-ui-settings`、`dsh-client-ui-settings-general`）在 rc.4 与 rc.5 的 npm 包：没有任何声明变化。三个 `lib/client.js` 有差异，且全部是构建内嵌内容——侧边栏换了新的构建串、设置页「关于」行里的版本号变成 rc.5、`dsh-api-remotes` 里 `packages/web/web/src/index.ts` 的源码行号位移。
- **安装要求不再写死「最新构建是哪个」。** 两份 README 原来写「`0.2.2` 预发布版本中最新已发布的是 `0.2.2-rc.4`」——三天后 DSH `0.2.2-rc.5` 就让这句话失真，而且以后每次 DSH 发版都得改。现在这句改成不会过期的事实：整个已发布的 `0.2.x` 线（含预发布）都在声明范围内，不论 npm 用哪个标签承载它；并说明了为什么上界写成针对发布线而不是某个构建。

### 兼容性与验证

- 声明范围没变：`dsh.engines.dsh` 与 `@deepseek-ai/dsh-settings` peer 都是 `>=0.1.7-alpha.2 <0.3.0`。上界是 `0.3.0` 这条线，`0.2.2-rc.5` 本来就在范围内。按本项目自 `0.5.0` 起的原则，范围内的 DSH 升级不需要插件「批准」。
- 在正在运行的 DSH `0.2.2-rc.5` 上实测：`POST /api/dsh-update-status.get-status` 返回 `200`，`currentVersion` 为 `0.2.2-rc.5` 且 `warning` 为 `null`；`restart-status` 正常返回 `supervisor: "launchd"`；`dsh-update-status/client.js` 出现在 `__DSH_BOOT__` 中；用无头 Chromium 打开真实 GUI，芯片显示 `0.2.2-rc.5` 与绿点，面板带 `data-window-drag-exclude=""` 正常打开，控制台零报错；Host 日志里没有本插件的兼容拒绝或错误。
- 没有任何设置项、profile 保存值、服务凭据或命令发生变化，升级不需要迁移；依然不自动安装、不自动重启。

### 升级到 0.5.3

```sh
dsh plugin --profile web add dsh-update-status@0.5.3
```

升级后重新加载页面。从 0.5.1 或 0.5.2 升上来，界面没有任何可见变化。

<h3 id="en-v0.5.3">Plugin 0.5.3 — re-checked against DSH 0.2.2-rc.5, and the "newest build" wording is gone</h3>

### Version matrix

| Plugin | What this version is | npm |
| --- | --- | --- |
| `0.5.3` | Checked against DSH `0.2.2-rc.5` (now npm's `latest`): no plugin code change; the install requirement no longer names a build that goes stale | This release, `latest` |
| `0.5.2` | Previous release: checked against DSH `0.2.2-rc.4`, also with no functional change | Published |

### What this version does

- **The only new upgrade-guide item does not apply.** Between `0.2.2-rc.4` and `0.2.2-rc.5` the sole new directory is `v0.2.2-rc.4`, holding one item, `web-search-deepseek-model-default`: DSH now defaults a search on a DeepSeek model route to legacy Messages search. This bundle registers no search or fetch provider and reads no `web.*` config, so it does not apply.
- **The injected client surface did not move.** Diffing the `0.2.2-rc.4` and `0.2.2-rc.5` npm tarballs of the seven packages this bundle injects (`dsh-settings`, `dsh-api-remotes`, `dsh-client-connection`, `dsh-client-ui-layout`, `dsh-client-ui-sidebar`, `dsh-client-ui-settings`, `dsh-client-ui-settings-general`) reports no declaration change. Three `lib/client.js` files differ, and every difference is build-embedded: the sidebar carries a new build string, the Settings About row renders the new version number, and `dsh-api-remotes` embeds shifted `sourceLocation` line numbers from `packages/web/web/src/index.ts`.
- **The install requirement stops naming a newest build.** Both READMEs said the `0.2.2` prereleases' "newest published build" was `0.2.2-rc.4`, which DSH `0.2.2-rc.5` falsified three days later — and which would have needed editing on every future DSH release. The sentence now states the durable fact: the whole published `0.2.x` line, prereleases included, is inside the declared range, whichever tag carries it; it also explains why the bound is written against the release line instead of a build.

### Compatibility and verification

- The declared range is unchanged: `dsh.engines.dsh` and the `@deepseek-ai/dsh-settings` peer both say `>=0.1.7-alpha.2 <0.3.0`. The upper bound is the `0.3.0` line, so `0.2.2-rc.5` was already inside it. Since `0.5.0` this project does not publish a per-release verification: a DSH release inside the range needs no plugin "approval".
- Verified on the running DSH `0.2.2-rc.5`: `POST /api/dsh-update-status.get-status` answers `200` with `currentVersion: "0.2.2-rc.5"` and `warning: null`; `restart-status` answers with `supervisor: "launchd"`; `dsh-update-status/client.js` is published in `__DSH_BOOT__`; a headless Chromium render of the real GUI shows the chip reading `0.2.2-rc.5` with its green dot and the panel opening with `data-window-drag-exclude=""`, zero console errors; and the Host log holds no compatibility refusal or error for this plugin.
- No setting, stored profile value, service receipt or command changes, and upgrading needs no migration. Nothing installs or restarts itself.

### Upgrade to 0.5.3

```sh
dsh plugin --profile web add dsh-update-status@0.5.3
```

Reload the page after upgrading. Coming from `0.5.1` or `0.5.2`, nothing you can see changes.
