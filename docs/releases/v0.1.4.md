<h3 id="cn-v0.1.4">插件 0.1.4 — 已验证 DeepSeek Harness 0.1.6-alpha.1</h3>

本版本修掉一个**通道选择死锁**：当 DSH 正在运行的版本恰好是某个通道指向的版本时，那一行会被隐藏，于是运行该版本的人反而无法关注这条通道。修复很小，但它解释了一次"偏好像是自己变了"的现象，下面一并说明。

### 版本对应

| 插件版本 | 已验证 DeepSeek Harness | npm 发布状态 | 该版本是什么 |
| --- | --- | --- | --- |
| **`0.1.4`** | `0.1.6-alpha.1`、`0.1.5-rc.1` | 本次发布（`latest`） | 修复"正在运行的通道不可选"；偏好写入路径补上回归测试 |
| `0.1.3` | `0.1.6-alpha.1`、`0.1.5-rc.1` | 已发布 | 含 `0.1.2` 的局域网修复，并在 0.1.6 上复验 |
| `0.1.2` | `0.1.5-rc.1` | 未发布 | 移除 `connection.isLoopback` 门控 |
| `0.1.1` | `0.1.5-rc.1` | 已发布 | 局域网/非回环页面下插件整体不可用 |
| `0.1.0` | `0.1.2-rc.1` | 已发布 | 首个版本 |

### 问题修复

- **「正在运行的通道」不再被隐藏。** 可选项过滤规则里有一条"版本号等于当前运行版本的通道不显示"。当 DSH 运行在 `alpha` 通道发布的版本（例如 `0.1.6-alpha.1`）而关注通道是 `next` 时，`alpha` 那一行会从详情面板和设置页的下拉框中**同时消失**——想关注这条线的人必须先关注它才能看到它。现在只在"前一行已经显示了同一个版本号"时才隐藏；如果所有通道都指向正在运行的版本，仍然只保留一行。
- **由此解释的一次"偏好自己变了"。** 在上面那种状态下，面板里唯一可点的另一行是 `稳定版（latest）`，点它就会真的把关注通道改成 `latest` 并写入 Host 设置文档。经排查，插件**没有任何自动写入偏好的路径**：能写 `channel` 的只有面板每行的「选择此通道」按钮和设置页下拉框，两处都是用户手势，没有 effect、定时器或挂载时写入。实测 4 类场景（3× 页面加载+开合面板、设置区块开合、2× 页面刷新、真实双击）写入数均为 0；profile 内其它插件的客户端包里也不存在 `settings.mutate` 或对 `dsh-update-status` 命名空间的引用。修复后这个把用户"引到唯一可点选项"的局面不再出现。
- **偏好写入路径现在有测试兜底。** 新增 `tests/client/entry.spec.ts` 用例：挂载真实客户端入口并接上官方 `settingsScope`，断言已持久化的偏好只被**读取**（最后一次状态读取使用存储的通道与缓存时长），且挂载与卸载全程 `set()` 调用为 0。把写入加回去会让这些用例失败。

### 改进

- `visibleChannelReleases` 的隐藏规则简化为"只去重版本号"，与"跟随通道是对将来的声明，不是对当前版本的声明"这一语义一致；相关注释写明了这次死锁的成因。
- 新增 2 个共享层测试：正在运行的通道仍可选；所有通道同版本时仍合并为一行。

### 兼容性与升级

- 已验证：DeepSeek Harness `0.1.6-alpha.1`、`0.1.5-rc.1`。
- 升级插件：

  ```sh
  dsh plugin --profile web add dsh-update-status@latest
  ```

- 如果你此前因为面板只给出 `latest` / `next` 而把关注通道改成了它们，升级后可以在面板里重新选回 `alpha`（运行 `0.1.6-alpha.1` 时它会正常出现在列表里）。
- 本插件仍然**只读**：不安装、不重启、不回滚、不下载、不替换任何文件。

<h3 id="en-v0.1.4">Plugin 0.1.4 — verified against DeepSeek Harness 0.1.6-alpha.1</h3>

This release fixes a **channel-selection deadlock**: when the release DSH is running happens to be the release a channel points at, that row was hidden — so an operator running that line could not follow it. The fix is small, but it explains a "my preference changed by itself" report, which is documented below.

### Version matrix

| Plugin | Verified DeepSeek Harness | On npm | What that version is |
| --- | --- | --- | --- |
| **`0.1.4`** | `0.1.6-alpha.1`, `0.1.5-rc.1` | this release (`latest`) | Fixes the unselectable running channel; adds regression tests for the preference write path |
| `0.1.3` | `0.1.6-alpha.1`, `0.1.5-rc.1` | published | Carries the `0.1.2` LAN fix, re-verified on 0.1.6 |
| `0.1.2` | `0.1.5-rc.1` | never published | Removed the `connection.isLoopback` gate |
| `0.1.1` | `0.1.5-rc.1` | published | The plugin is inert on LAN/non-loopback pages |
| `0.1.0` | `0.1.2-rc.1` | published | First release |

### Bug Fixes

- **The channel you are running is no longer hidden.** The candidate filter dropped any channel whose version equalled `currentVersion`. With DSH running a release published on `alpha` (for example `0.1.6-alpha.1`) while following `next`, the `alpha` row disappeared from both the detail panel and the settings select — the one line such an operator would want to follow could only be seen by already following it. A row is now hidden only when an earlier row already shows the same version; when every channel points at the running release, the list still collapses to one row.
- **The preference change this explains.** In exactly that state the only other selectable row was `稳定版（latest）`, and clicking it really does set the followed channel to `latest` and write it to the Host document. The audit found **no automatic write path**: only the panel's per-channel button and the settings select can write `channel`, both user gestures, with no effect, timer, or mount-time write. Four scenario families (3× page load plus panel open/close, settings-section open/reopen, 2× page reload, and a real coordinate double-click) produced zero writes, and no other plugin in the profile has `settings.mutate` or any reference to the `dsh-update-status` namespace in its client bundle. The fix removes the situation that steered the operator to the only clickable row.
- **The preference write path now has test cover.** `tests/client/entry.spec.ts` mounts the real client entry with the official `settingsScope` seam present and asserts that a persisted preference is applied by *reading* (the last status read follows the stored channel and cache policy) and that mount plus teardown issue zero `set()` calls. Re-adding such a write fails those cases.

### Improvements

- `visibleChannelReleases` now hides rows only by version de-duplication, matching the semantics that following a channel is a statement about future releases rather than about the running one; the comments record how the deadlock arose.
- Two new shared-layer tests: the channel currently pointing at the running release stays selectable; channels that all share one version still collapse to a single row.

### Compatibility and upgrade

- Verified: DeepSeek Harness `0.1.6-alpha.1` and `0.1.5-rc.1`.
- Upgrade the plugin:

  ```sh
  dsh plugin --profile web add dsh-update-status@latest
  ```

- If you previously switched the followed channel to `latest` or `next` because the panel only offered those, you can pick `alpha` again after upgrading — it now appears normally while `0.1.6-alpha.1` is running.
- The plugin remains **read-only**: it never installs, restarts, rolls back, downloads, or replaces files.
