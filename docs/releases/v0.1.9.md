**兼容的最新 DSH 版本：`0.1.7-rc.2`**（npm `next` 通道当前指向它）。本版同时覆盖 `0.1.7-rc.1` 与 `0.1.7-alpha.2`，已验证清单与 `0.1.8` 完全一致——本版不新增 DSH 版本。

### 为什么发这个版本

有一类机器上，**升级 DSH 之后再升级本插件，插件会整个消失**：侧栏入口、详情面板、设置区全部不再出现，页面本身没有任何提示，宿主日志里只有一行

```text
TypeError: z.boolean(...).default(...).volatile is not a function
```

同一台 DSH 版本、同一个插件版本，在另一台机器上却完全正常。这不是版本差异，而是一份**被遮蔽的 peer 依赖**：

- `0.1.0`–`0.1.5` 把 `@deepseek-ai/schemastery` 声明为普通 **dependency**（`^3.18.2`），宿主半从不调用 `volatile()`；
- `0.1.6` 起它改为**由 DSH 提供的 peer**（`^3.18.4`），宿主半开始用 `volatile()` —— 而 `volatile()` 是 **DSH 给 schemastery 打的补丁**，只存在于平台那份 3.18.4 里；
- 宿主半原来写的是 `import z from '@deepseek-ai/schemastery'`，Node 按**导入文件的位置**逐级向上解析，因此插件安装目录里残留的一份旧副本会先被命中；
- 那份残留是**非 pnpm 创建**的实体目录（用本地目录安装时被一起拷进来的 dev `node_modules`，pnpm 在后续升级中永远不会清理它）。

于是「升 DSH + 升插件」把这份残留从无害变成致命：旧代码不调 `volatile()` 时它毫无影响，新代码一调就在 **import 阶段**抛错——**早于任何插件代码运行**，所以连自修的机会都没有，升级插件本身也修不好。

需要说明的是：pnpm 自己创建的副本（根级 hoisted、版本冲突时嵌套的软链）在升级时会被正常剪掉，所以**一直用 registry 安装/升级的用户本来就是安全的**。中招的是曾经用本地目录装过插件、或 profile 里被塞进过实体 `node_modules` 的环境。

### 改了什么

- **阴影免疫：宿主半不再用裸说明符拿这个 peer。** 新增 [`src/host/schemastery.ts`](../../src/host/schemastery.ts)，改为自己解析，顺序**平台优先**：运行中的 DSH 安装 → profile peer 农场（`$DSH_HOME/profiles/node_modules`）→ 当前 profile 自身树 → 最后才回落到 Node 的目录游走。取**第一个真的具备 `volatile()`** 的候选（用 `boolean().default(true).volatile` 实测，不是假设），并同时兼容 `module.exports` 直接导出与 `default` 包装两种形状。构建产物现在**零裸模块导入**，只剩 `node:*`。
- **永不 import 期抛错。** 只找得到旧副本时插件照样加载：[`src/host/settings.ts`](../../src/host/settings.ts) 拆出 `buildConfigSchema(factory, volatileAvailable)`，用普通字段构建 `Config`；宿主日志打印实际解析结果；面板给出新的 `stale-schemastery` 提示（严重级别 `notice`，**不会把芯片染红**），写明版本、解析到的路径，以及该删除的目录。只有**完全解析不到**（即不在可用的 DSH 安装内运行）才抛错，且会列出每个候选的失败原因。
- **三重回归守卫。** [`tests/host/schemastery.spec.ts`](../../tests/host/schemastery.spec.ts) 用注入候选驱动解析（平台副本胜过遮蔽副本 / 只有旧副本时照常加载并报告 / 无法解析的候选被跳过 / 默认顺序平台在前），并含一条**源码守卫**：任何 `src/` 文件再次对它取**值导入**即失败。[`tests/guards/shadowed-peer.mjs`](../../tests/guards/shadowed-peer.mjs) 对**构建产物**下手：在入口旁放一份伪造的 `3.18.2`，断言仍能加载，且平台副本存在时必须是平台副本获胜。该守卫已接入 `pnpm run verify`、CI 与两个 release workflow（均在 build 之后）。
- **文档。** 中英文 README 新增对应故障排查条目（含手工清理命令）；`CHANGELOG.md` 同步。

### 谁受影响

- **插件已经消失的人：本版就是给你的。** 但请注意顺序——已经运行 `0.1.6`–`0.1.8` 且属于「实体残留」的环境**无法加载任何更新的版本**（故障发生在插件代码运行之前），必须先手工删除残留目录，再重启 DSH：

  ```sh
  rm -rf ~/.dsh/profiles/<profile>/node_modules/dsh-update-status/node_modules
  dsh plugin --profile web add dsh-update-status@0.1.9
  ```

  删除后从本版起，**升级插件本身就是修复**，残留即使再出现也不会再让插件消失。
- **一直用 registry 安装、升级的人：本来就是安全的**，本版只是把这类风险彻底去掉，行为没有变化。
- **从 `0.1.8` 升级：无需任何迁移。** 偏好仍是 profile patch 中 `dsh-update-status` 条目的 `config`，三个偏好字段仍是唯一的 volatile 字段。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续使用插件 `0.1.5`。** `0.1.6` 及之后声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`，范围不匹配的 bundle 会在 profile 加载阶段被拒绝。

### 兼容性与升级

```sh
dsh plugin --profile web add dsh-update-status@0.1.9
```

宿主半边只在 DSH 启动时加载，因此**需要重启 `dsh web`**；客户端半边刷新页面即生效。`dsh.engines.dsh`、`peerDependencies` 与已验证 DSH 清单均未改动。

### 验证

- `pnpm run verify`：`tsc --noEmit`（src + tests）、**116/116** vitest（15 个测试文件，原 98）、tsdown 构建、`guard:shadowed-peer`、`pnpm pack --dry-run` 全部通过。
- **构建产物导入检查**：`lib/index.js` 的裸模块导入为 0，只剩 `node:*`。
- **真实损坏环境实测**：把某台机器 profile 里那份真实的 `3.18.2` 残留挂在插件目录旁，新构建 `IMPORT OK`，解析到 DSH 安装内的 `3.18.4`，`volatile` 可用、无告警；同一布局下旧构建抛 `TypeError`。
- **守卫双场景**：只有旧副本 → 加载成功并报 `stale-schemastery`（含应删除目录）；有平台副本 → `via profile-peers`、`volatile available`。该守卫已在 Linux CI（Node 24）上实际跑通。
- **诚实的边界**：本版**没有**做面板与芯片在真实 `dsh web` 会话里的端到端交互复核；上面验证的是「宿主半能否加载、解析到哪一份、守卫是否守住」。安装后请在侧栏确认版本 Badge、详情面板与设置区是否正常。

### 限制

- **本版修不了「已经坏掉」的安装**：`0.1.6`–`0.1.8` 遇到实体残留时无法加载，必须先手工删除残留（见上）。
- **偏好设置属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享；同一实例下多浏览器/设备共享那一份 profile patch 条目。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写这些偏好。
- **非回环页面依赖插件自己的直连通道**：DSH 官方策略是不为非 loopback 页面持久化设置，插件为此额外走一次公开 Remote；若未来 DSH 改动该 Remote 的形状，局域网页面会退回「只读 + 默认值」。

### Why this release exists

On some machines, **upgrading DSH and then upgrading this plugin made the plugin disappear entirely**: no sidebar entry, no detail panel, no settings section, nothing on the page to explain it, and only one line in the host log:

```text
TypeError: z.boolean(...).default(...).volatile is not a function
```

The same DSH version and the same plugin version worked on another machine. That is not a version difference — it is a **shadowed peer dependency**:

- `0.1.0`–`0.1.5` declared `@deepseek-ai/schemastery` as a regular **dependency** (`^3.18.2`) and never called `volatile()`;
- from `0.1.6` it is a **peer that DSH provides** (`^3.18.4`), and the host half calls `volatile()` — a method **DSH adds to schemastery**, present only in the platform's 3.18.4;
- the host half used to write `import z from '@deepseek-ai/schemastery'`, which Node resolves *upward from the importing file*, so a stale copy inside the plugin's own install directory was found first;
- that leftover is an **unmanaged** directory (a dev `node_modules` copied in by a local-directory install, which pnpm never removes during later upgrades).

Upgrading DSH and then the plugin turned that leftover from harmless into fatal: old code never called `volatile()`, new code calls it during **import**, which is **before any plugin code runs** — so nothing inside the plugin can repair it, and upgrading the plugin alone cannot fix it either.

To be precise about the blast radius: copies pnpm itself created (a hoisted root copy, or a nested symlink from a version conflict) are pruned on upgrade, so **users who only ever installed and upgraded from the registry were already safe**. The affected environments are those that installed the plugin from a local directory at least once, or that have an unmanaged `node_modules` inside the profile.

### What changed

- **Shadow-proof resolution: the host half no longer takes this peer by bare specifier.** [`src/host/schemastery.ts`](../../src/host/schemastery.ts) resolves it directly, platform copies first: the running DSH installation → the profile peer farm (`$DSH_HOME/profiles/node_modules`) → the active profile's own tree → and only then Node's walk. The first candidate that **actually exposes `volatile()`** wins (probed with `boolean().default(true).volatile`, not assumed), and both CommonJS shapes are accepted (`module.exports` directly, or wrapped in `default`). The built host half now has **zero bare module imports** — only `node:*`.
- **It never throws while being imported.** When only a stale copy is reachable the plugin still loads: [`src/host/settings.ts`](../../src/host/settings.ts) exposes `buildConfigSchema(factory, volatileAvailable)` and builds `Config` with ordinary fields; the Host logs what it resolved; and the panel shows a new `stale-schemastery` warning (severity `notice`, so **the chip never repaints**) naming the version, the resolved path and the directory to remove. Only a **total miss** — no schemastery anywhere, meaning the plugin is not running inside a working DSH installation — still throws, and it names every candidate it tried.
- **Three regression guards.** [`tests/host/schemastery.spec.ts`](../../tests/host/schemastery.spec.ts) drives the resolver with injected candidates (platform copy beats a shadowing copy; a stale-only environment loads and reports; unresolvable candidates are skipped; the default order is platform-first) plus a **source guard** that fails if any file under `src/` takes a **value** import of the peer again. [`tests/guards/shadowed-peer.mjs`](../../tests/guards/shadowed-peer.mjs) works on the **built artifact**: it plants a fake `3.18.2` beside the entry, asserts it still loads, and asserts the platform copy wins when one is present. The guard runs in `pnpm run verify`, CI and both release workflows, after the build.
- **Docs.** Both READMEs gained the matching troubleshooting entry (including the manual cleanup command), and `CHANGELOG.md` was updated.

### Who is affected

- **If the plugin already disappeared: this release is for you.** But mind the order — an environment already running `0.1.6`–`0.1.8` with an unmanaged leftover **cannot load any newer version either** (the failure happens before plugin code runs), so remove the leftover and restart DSH first:

  ```sh
  rm -rf ~/.dsh/profiles/<profile>/node_modules/dsh-update-status/node_modules
  dsh plugin --profile web add dsh-update-status@0.1.9
  ```

  After that, from this version on **upgrading is the whole fix**: a leftover can no longer take the plugin down.
- **If you only ever installed and upgraded from the registry: you were already safe.** This release removes the risk class entirely; behaviour is unchanged.
- **Upgrading from `0.1.8`: no migration.** Preferences remain this entry's `config` in the profile patch, and the three preferences remain the only volatile fields.
- **Still on an older DSH (including `0.1.6-alpha.2`): stay on plugin `0.1.5`.** `0.1.6` and newer declare `>=0.1.7-alpha.2 <0.2.0`, and a bundle outside that range is refused at profile load.

### Compatibility and upgrade

```sh
dsh plugin --profile web add dsh-update-status@0.1.9
```

The host half loads only when DSH starts, so **restart `dsh web`**; the client half takes effect on a page refresh. `dsh.engines.dsh`, the peer declarations and the verified DSH list are all unchanged.

### Verification

After installing, confirm the version badge, the detail panel and the settings section in the sidebar.

### Limitations

- **This release cannot repair an already-broken install.** `0.1.6`–`0.1.8` cannot load when an unmanaged leftover is present; the leftover must be removed by hand first (see above).
- **Preferences belong to one DSH instance**: they are not shared between two independent DSH services, and multiple browsers/devices on one instance share that single profile-patch entry.
- **There is no permission model**: anyone who can reach the profile's authenticated routes can read and write those preferences.
- **Non-loopback pages depend on the plugin's own direct channel**: DSH's stock policy never persists settings for a non-loopback page, so the plugin takes one extra public Remote; if DSH changes that Remote's shape, LAN pages fall back to read-only defaults.
