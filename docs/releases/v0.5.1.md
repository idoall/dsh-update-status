<h3 id="cn-v0.5.1">插件 0.5.1 — macOS 桌面版上面板的按钮照常可点</h3>

### 版本对应

| 插件 | 该版本是什么 | npm |
| --- | --- | --- |
| `0.5.1` | 按 DSH `0.2.2` 的新窗口区域规则修正面板；开发依赖跟进到 DSH `0.2.2-rc.3` | 本次发布，`latest` |
| `0.5.0` | 上一次发布：一个可升级版本一张卡片，删除兼容台账 | 已发布 |

### 问题修复

- **在 macOS 桌面版上，面板的按钮不再变成拖窗口。** DSH `0.2.2-rc.2` 收窄了 macOS 的拖动排除范围：以前页面上任何匹配的交互控件都会被排除，现在只有 `data-window-drag` 行或 `data-window-drag-controls` 范围内的控件才算。会话头部、插件管理页、设置 → 账号都把自己标成拖动行，而本插件的面板开在 `top: 12px`、`left: 292px`，正好压在会话头部的拖动行上。
- 受影响的是面板里的每一个可点元素：**检查更新**、**发布说明**、**重启**、缓存输入框和 **×**。没有声明窗口区域时，在 macOS 桌面版上点它们会让整个窗口开始拖动，看起来像「按钮失灵」。
- 修法是官方给出的迁移方式：在面板自己那块可滚动的盒子上声明 `data-window-drag-exclude`，也就是「没有嵌套拖动行的交互视口」的做法。排除范围刚好等于面板本身；全屏背景层刻意不声明区域，否则面板打开期间整个窗口都拖不动。
- 纯 Web 与 Windows 不受影响：它们从来没有那套自动排除，这个属性在那边是惰性的；在 `0.2.2-rc.2` 之前的 DSH 上同样无害。

### 改进

- **开发依赖跟进到当前 DSH。** `@deepseek-ai/dsh-settings` 从 `0.1.7-alpha.2` 提到 `0.2.2-rc.3`，`@deepseek-ai/cordis` 提到 `^4.1.0`，`@deepseek-ai/schemastery` 提到 `^3.19.0`。两套类型检查与全部 241 个测试现在跑在当前 Host 真正发布的 API 上，而不是 `0.1.7` 那条线；对外声明的 peer 范围没有收紧，老版本 DSH 照旧被接纳。
- **把整个面都过了一遍，而不是只改一处。** 从 `v0.2.1-rc.4` 到 `v0.2.2-rc.1` 的 49 条升级指南逐条对照本插件的接触面，只有 `window-drag-regions` 命中：bundle 里没有 `pluginManager` / `BundleInfo.updatable`、右键菜单、`Menu` 定位、Session 投影、Schedule、Office、LLM 错误码或文件系统策略相关代码。
- **在实际运行的 Host 上验证，而不是推测。** 在 DSH `0.2.2-rc.3` 上：`POST /api/dsh-update-status.get-status` 返回 `200`，`currentVersion` 是 `0.2.2-rc.3` 且没有警告；重启状态与重启检查两个 RPC 正常返回，`supervisor` 为 `launchd` 并带上正在运行的会话列表；`dsh-update-status/client.js` 出现在 `__DSH_BOOT__` 里；用无头 Chromium 打开真实 GUI，芯片显示 `0.2.2-rc.3` 与绿点，面板带 `data-window-drag-exclude=""`，控制台零报错。六个注入包在 `0.2.2-rc.3` 下都仍然存在。

### 可加载性与升级

- 版本范围没变：`dsh.engines.dsh` 与 `@deepseek-ai/dsh-settings` peer 都是 `>=0.1.7-alpha.2 <0.3.0`。上界是 `0.3.0` 这条线，`0.2.2-rc.3` 本来就在范围内——这次发版不是为某个 DSH 版本「开权限」，只是修掉 `0.2.2` 线改动带来的一个 macOS 桌面版行为。
- 没有任何设置项、profile 里保存的值、服务凭据或命令发生变化，升级不需要迁移。
- 仍然不自动安装、不自动重启；面板里的命令永远靠你自己执行。

```sh
dsh plugin --profile web add dsh-update-status@0.5.1
```

升级后重新加载页面。

<h3 id="en-v0.5.1">Plugin 0.5.1 — the panel's buttons keep working on macOS Desktop</h3>

### Version matrix

| Plugin | What this version is | npm |
| --- | --- | --- |
| `0.5.1` | Corrects the panel for the DSH `0.2.2` window-region rule; devDependencies follow DSH `0.2.2-rc.3` | This release, `latest` |
| `0.5.0` | Previous release: one card per upgradable version, compatibility ledger removed | Published |

### Bug Fixes

- **On macOS Desktop, the panel's buttons no longer start a window drag.** DSH `0.2.2-rc.2` narrowed macOS drag exclusion: previously any matching interactive control anywhere in the page was excluded, now only controls inside a `data-window-drag` row or a `data-window-drag-controls` scope are. The conversation header, the plugin manager and Settings → Account all mark themselves as drag rows, and this plugin's panel opens at `top: 12px`, `left: 292px` — directly over the conversation header's drag row.
- Every clickable control in the panel was affected: **Check for updates**, **Release notes**, **Restart**, the cache input and **×**. Without a declared window region, pressing them on macOS Desktop dragged the window instead, which reads as "the button does nothing".
- The fix is the documented migration: declare `data-window-drag-exclude` on the panel's own scrolling box, the rule for "an interactive viewport without nested drag rows". The exclusion covers exactly the panel; the full-viewport backdrop deliberately declares no region, because excluding it would make the whole frame undraggable while the panel is open.
- Plain Web and Windows are unaffected: they never had that automatic exclusion, and the attribute is inert there. On a DSH older than `0.2.2-rc.2` it is equally harmless.

### Improvements

- **devDependencies follow the running DSH.** `@deepseek-ai/dsh-settings` moves from `0.1.7-alpha.2` to `0.2.2-rc.3`, `@deepseek-ai/cordis` to `^4.1.0`, `@deepseek-ai/schemastery` to `^3.19.0`. Both type checks and all 241 tests now run against the APIs the current Host actually ships instead of the `0.1.7` line; the declared peer ranges did not tighten, so older DSH releases are still accepted.
- **The whole surface was reviewed, not one item.** All 49 upgrade-guide items from `v0.2.1-rc.4` through `v0.2.2-rc.1` were read against the plugin's surfaces; only `window-drag-regions` applies. The bundle contains no `pluginManager` / `BundleInfo.updatable`, context-menu, `Menu` positioning, Session projection, Schedule, Office, LLM-error or filesystem-policy code.
- **Checked on the running Host, not assumed.** Under DSH `0.2.2-rc.3`: `POST /api/dsh-update-status.get-status` answers `200` with `currentVersion: "0.2.2-rc.3"` and no warning; the restart-status and restart-check RPCs answer normally with `supervisor: "launchd"` and the live session list; `dsh-update-status/client.js` is published in `__DSH_BOOT__`; and a headless Chromium render of the real GUI shows the chip reading `0.2.2-rc.3` with its green dot and the panel carrying `data-window-drag-exclude=""`, with zero console errors. All six injected packages still exist at `0.2.2-rc.3`.

### Loadability and upgrade

- The declared range is unchanged: `dsh.engines.dsh` and the `@deepseek-ai/dsh-settings` peer both say `>=0.1.7-alpha.2 <0.3.0`. The upper bound is the `0.3.0` line, so `0.2.2-rc.3` was already inside it — this release is not a permission slip for a DSH version, it fixes one macOS Desktop behaviour the `0.2.2` line changed.
- No setting, stored profile value, service receipt or command changes, and upgrading needs no migration.
- Nothing installs or restarts itself; every command the panel shows is one you run.

```sh
dsh plugin --profile web add dsh-update-status@0.5.1
```

Reload the page after upgrading.
