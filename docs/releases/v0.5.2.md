<h3 id="cn-v0.5.2">插件 0.5.2 — 按 DSH 0.2.2-rc.4 复核：插件代码无需改动</h3>

### 版本对应

| 插件 | 该版本是什么 | npm |
| --- | --- | --- |
| `0.5.2` | 按 DSH `0.2.2-rc.4` 复核的维护版：中英文 README 与开发依赖更新到该版本，功能代码不变 | 本次发布，`latest` |
| `0.5.1` | 上一次发布：按 DSH `0.2.2` 新的窗口区域规则修正面板 | 已发布 |

### 本版做了什么

- **没有需要修的东西。** 从 DSH `0.2.2-rc.3` 到 `0.2.2-rc.4`，新的升级指南目录只有一个 `v0.2.2-rc.3`，其中仅一条：DeepSeek 流式拒答的结束码由 `MALFORMED_RESPONSE` 改为 `CONTENT_REFUSED`。这属于 LLM 错误分类，本插件根本不处理错误码，因此不涉及。
- `0.5.1` 修的那条（`v0.2.2-rc.1` 的 `window-drag-regions`：macOS 桌面版只排除标记行内的控件）在 rc.4 中没有变化，修法继续有效。
- **注入的客户端接口没有变化。** 对比 `dsh-settings`、`dsh-api-remotes`、`dsh-client-connection`、`dsh-client-ui-layout`、`dsh-client-ui-sidebar` 五个包在 rc.3 与 rc.4 的 npm 包：没有任何声明或导出变化；唯一不同的是 `dsh-client-ui-sidebar/lib/client.js`，而把内嵌的构建版本串（`0.2.2-rc.3-6b729fe` → `0.2.2-rc.4-70005a5`）归一化后，两个文件逐字节相同。
- **为什么仍然发一版。** 两份 README 都把 `0.2.2-rc.3` 写成「最新已发布的 DSH 构建」，而发布包里的 `devDependencies` 也仍钉在 `@deepseek-ai/dsh-settings@0.2.2-rc.3`——也就是说类型检查和测试跑的是上一版的声明。这两处现在都已更新到 rc.4，npm 上供下载的包里就是这些内容。

### 兼容性与验证

- 声明的范围没变：`dsh.engines.dsh` 与 `@deepseek-ai/dsh-settings` peer 都是 `>=0.1.7-alpha.2 <0.3.0`。上界是 `0.3.0` 这条线，`0.2.2-rc.4` 本来就在范围内。按本项目自 `0.5.0` 起的原则，范围内的 DSH 升级不需要插件「批准」，这次发版只是把文档和依赖对齐。
- 在正在运行的 DSH `0.2.2-rc.4` 上实测：`POST /api/dsh-update-status.get-status` 返回 `200`，`currentVersion` 为 `0.2.2-rc.4` 且 `warning` 为 `null`；`restart-status` 正常返回 `supervisor: "launchd"` 与当前实例 id；`dsh-update-status/client.js` 出现在 `__DSH_BOOT__` 中；用无头 Chromium 打开真实 GUI，芯片显示 `0.2.2-rc.4` 与绿点，面板带 `data-window-drag-exclude=""` 正常打开，控制台零报错；Host 日志中没有本插件的兼容拒绝或错误。
- 没有任何设置项、profile 里保存的值、服务凭据或命令发生变化，升级不需要迁移；依然不自动安装、不自动重启。

### 升级到 0.5.2

```sh
dsh plugin --profile web add dsh-update-status@0.5.2
```

升级后重新加载页面。若你已经在 0.5.1 上，这次升级对界面没有任何可见变化。

<h3 id="en-v0.5.2">Plugin 0.5.2 — re-checked against DSH 0.2.2-rc.4: no plugin code change was needed</h3>

### Version matrix

| Plugin | What this version is | npm |
| --- | --- | --- |
| `0.5.2` | Maintenance release re-checked against DSH `0.2.2-rc.4`: both READMEs and the devDependency line move to that build, functional code unchanged | This release, `latest` |
| `0.5.1` | Previous release: corrected the panel for the DSH `0.2.2` window-region rule | Published |

### What this version does

- **There was nothing to fix.** Between DSH `0.2.2-rc.3` and `0.2.2-rc.4` the only new upgrade-guide directory is `v0.2.2-rc.3`, and it holds one item: the DeepSeek streamed refusal finish code becomes `CONTENT_REFUSED` instead of `MALFORMED_RESPONSE`. That is LLM error classification; this bundle implements no such handling, so it does not apply.
- The item `0.5.1` addressed (`window-drag-regions` from the `v0.2.2-rc.1` line: macOS Desktop excludes only controls inside marked drag rows) is unchanged in `0.2.2-rc.4`, and the fix remains in place.
- **The injected client surface did not move.** Diffing the `0.2.2-rc.3` and `0.2.2-rc.4` npm tarballs of `dsh-settings`, `dsh-api-remotes`, `dsh-client-connection`, `dsh-client-ui-layout` and `dsh-client-ui-sidebar` reports no declaration or export change. The single differing file is `dsh-client-ui-sidebar/lib/client.js`, and once its embedded build string (`0.2.2-rc.3-6b729fe` → `0.2.2-rc.4-70005a5`) is normalised, the two files are byte-identical.
- **Why publish anyway.** Both READMEs named `0.2.2-rc.3` as the newest published DSH build, and the shipped package still pinned `@deepseek-ai/dsh-settings@0.2.2-rc.3`, so the type checks and test suite were exercising the previous release's declarations. Both now name `0.2.2-rc.4`, and that is what npm serves.

### Compatibility and verification

- The declared range is unchanged: `dsh.engines.dsh` and the `@deepseek-ai/dsh-settings` peer both say `>=0.1.7-alpha.2 <0.3.0`. The upper bound is the `0.3.0` line, so `0.2.2-rc.4` was already inside it. Since `0.5.0` this project does not publish a per-release verification: a DSH release inside the range needs no plugin "approval", and this release only aligns the documentation and the dependency line.
- Verified on the running DSH `0.2.2-rc.4`: `POST /api/dsh-update-status.get-status` answers `200` with `currentVersion: "0.2.2-rc.4"` and `warning: null`; `restart-status` answers with `supervisor: "launchd"` and the current instance id; `dsh-update-status/client.js` is published in `__DSH_BOOT__`; a headless Chromium render of the real GUI shows the chip reading `0.2.2-rc.4` with its green dot and the panel opening with `data-window-drag-exclude=""`, with zero console errors; the Host log holds no compatibility refusal or error for this plugin.
- No setting, stored profile value, service receipt or command changes, and upgrading needs no migration. Nothing installs or restarts itself.

### Upgrade to 0.5.2

```sh
dsh plugin --profile web add dsh-update-status@0.5.2
```

Reload the page after upgrading. If you are already on `0.5.1`, this upgrade changes nothing you can see.
